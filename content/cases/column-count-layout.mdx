시험지는 학생 손에 인쇄되어 쥐어지는 순간 완성된다. 지문이 중간에서 뭉텅 잘려 나간 시험지는 그 자체로 치명적인 불량품이었다.

웹은 끝없는 스크롤의 세상이지만, 인쇄물은 엄격한 A4 고정 규격의 세상이다. 2년 동안 여러 프리랜서와 사내 개발자들이 이 간극을 메우려 시도했다가 두 손을 들었고, 인쇄 불량으로 인한 환불 문의는 매일같이 쏟아지고 있었다.

입사 직후, 챕터 리드께서 조용히 다가와 이 과제를 건네며 중요한 힌트를 하나 얹어주셨다.

> "채용 과제에서 보여주신 창의적인 접근 방식이 인상 깊어서 훈조 님께 기대가 커요. 사실 그동안 거쳐 간 프리랜서들과 개발자들 모두가 달라붙었지만 결국 못 풀었던 문제입니다. 예전에 `column-count`를 써서 브라우저 다단으로 해결해보려다 실패했던 적도 있고요. 훈조 님이 풀어주시면 가장 좋겠지만, 회사 모두가 얼마나 어려운 문제인지 알고 있으니 너무 부담은 갖지 마세요."

"모두가 실패했던 난제이니 부담 갖지 말라"는 말은 역설적으로 엔지니어의 승부욕을 자극했고, 리드가 지나가듯 던져준 **과거에 column-count로 풀려다 실패했다는 힌트**가 머릿속에 깊게 박혔다.

'실패한 방식이니 피해야지'가 아니라, **왜 하필 다단 CSS를 쓰려 했을까? 그리고 왜 실패했을까?**를 파고들며 실패의 역사를 분해하는 것부터 시작했다.

## 문제: 브라우저는 페이지를 모른다

교육 콘텐츠 편집기에서 문제들을 실제 인쇄물처럼 A4 2단(Multi-column) 페이지로 자동 분할해 배치해야 했다. 기존 구현은 일반적인 짧은 카드의 높이를 측정해 두 열에 번갈아 배치하는 단순한 방식이었다. 하지만 **한 열의 높이를 훌쩍 넘는 긴 지문 카드**가 들어오는 순간 시스템은 완전히 무너졌다.

웹 표준 CSS로는 이 문제를 정석적으로 풀 수 없었다:

1. **브라우저 다단(`column-count: 2`)은 페이지 개념이 없다**: 브라우저의 CSS 다단은 가로로 무한히 늘어날 뿐, "2개 열이 꽉 차면 다음 A4 페이지의 1열로 넘긴다"는 페이지 분할 규칙 자체가 웹 명세에 존재하지 않는다.
2. **화면과 PDF 렌더의 괴리**: 화면에서는 문제 호버, 선택, 드래그 같은 인터랙션이 돌아야 하고, 서버에서는 동일한 HTML을 넘겨받아 무결한 PDF로 구워내야 했다. 브라우저 네이티브 다단은 둘 사이의 일관성을 제어할 수 없었다.
3. **픽셀 절단의 참사**: 그렇다고 DOM 요소를 자바스크립트로 특정 픽셀(px) 높이에서 잘라버리면, 글자 허리가 반토막 나거나 줄 간격이 뭉개진 채 인쇄되었다.

글자가 깨지지 않으면서, 긴 카드가 여러 열과 페이지를 물 흐르듯 가로지르는 다단 페이지네이션 엔진이 절실했다.

## 다섯 번의 시도와 가설의 붕괴

정답에 도달하기까지 다섯 번을 갈아엎었다. 하지만 각 단계의 실패는 다음 시도의 결정적인 재료가 되어주었다.

### 1. Canvas 캡처와 픽셀 크롭: 픽셀로 자르면 안 된다
작은 카드는 DOM으로 두고, 한 열보다 긴 카드는 캔버스로 캡처해 픽셀 단위로 잘라냈다. 하지만 줄 간격을 무시하고 기계적으로 자르다 보니 글자 윗부분과 아랫부분이 동강 났다. 텍스트 사이 빈 여백을 감지해 자르는 보정 로직을 얹었지만 연산 비용이 치솟았고 성능이 무너졌다.
- **얻은 교훈**: 글자는 픽셀이 아니라 브라우저의 텍스트 줄(Line) 단위로 자연스럽게 나뉘어야 한다.

### 2. 컨테이너 전체에 `column-count` 적용: 화면 전체를 감싸면 죽는다
브라우저 다단 엔진에 줄 자르기를 맡기기로 했다. 문제는 2열이 끝난 뒤 다음 페이지로 넘길 방법이 없다는 점이었다. 각 페이지마다 전체 카드를 담은 거대한 컨테이너를 통째로 넣고 `translateX`로 해당 페이지만 보이도록 마스킹했다. 하지만 1,000개 카드가 10페이지에 걸치면 10,000개의 DOM 노드가 복제되었다. 브라우저는 렌더링 블락으로 멈춰 섰다. 청크 분할, 이중 `requestAnimationFrame`, `flushSync`를 쏟아부어도 페이지 전환 딜레이를 잡을 수 없었다.
- **얻은 교훈**: `column-count`는 텍스트를 아름답게 넘겨주지만, 화면 전체를 통째로 감싸 복제하면 렌더링이 죽는다.

### 3. 글자 단위 바이너리 서치 높이 측정: DOM 텍스트 실측의 한계
DOM의 모든 단어를 `inline-block`으로 쪼갠 뒤, 컨테이너 높이를 넘치는 글자 인덱스를 이진 탐색(Binary Search)으로 찾았다. 연산량은 줄였으나 폰트 렌더링 타이밍, 패딩, 복잡한 수식과 서식 탓에 "진짜 마지막 글자"의 좌표가 흔들렸다. 엣지케이스가 끝없이 터져 나왔다.
- **얻은 교훈**: 자바스크립트로 DOM 텍스트 좌표를 일일이 계산하는 것은 폰트와 줌에 취약하며 유지보수가 불가능하다.

### 4. 실패의 교차 결합: 1번의 실패를 2번으로 덮다
발상을 전환했다. 1번이 못 했던 "글자 안 깨지는 줄바꿈"을 2번의 `column-count`가 브라우저 레벨에서 무료로 제공한다. 그래서 긴 카드가 포함된 페이지만 골라 다단을 걸었다. 하지만 긴 카드가 다음 페이지로 넘어가면 나머지 짧은 카드들도 다음 페이지에 줄줄이 복제되어야 해서, 여전히 페이지가 늘어날수록 불필요한 DOM 복제가 누적되었다.

### 5. 결정적 묘수: 긴 카드 하나하나를 `column-count: 1`로 감싸기
여기서 모든 퍼즐이 맞춰졌다. 컨테이너 전체가 아니라, **잘려야 하는 긴 카드 딱 하나에만 `column-count: 1`과 고정 높이를 부여**했다.

높이가 제한된 박스에서 `column-count: 1`을 만나면, 브라우저는 넘치는 텍스트를 글자 하나 다치지 않고 보이지 않는 옆의 가상 열로 흘려보낸다. 우리는 1열에서 잘린 그 카드 조각만 다음 열에 복제하고, 가로축(`translateX`)을 컬럼 폭만큼 이동시켜 이어 붙였다.

```text
긴 카드 — 한 컬럼 높이를 넘는다
┌────┐
│ 1  │
│ 2  │
│ …  │
└────┘

column-count:1 + 고정 높이로 클립 → 넘친 만큼 옆 가상 컬럼으로 흐른다
┌────┬────┬────┐
│ 1  │ 3  │ 5  │
│ 2  │ 4  │ 6  │
└────┴────┴────┘
잘린 조각만 다음 컬럼에 복제하고 translateX로 이어 붙인다
```

1번에서 실패한 "카드 단위 크롭"과 2번에서 실패한 "브라우저 다단 엔진"을 합쳐, **다단 CSS를 레이아웃이 아니라 '글자 안 깨지는 정밀 가위'로 역이용한 것**이다.

## 한 번에 끝나지 않았다 — 3세대 아키텍처 진화

이 알고리즘은 사내 전용 코드로 머물지 않고 독립 오픈소스 패키지(`column-pager`)로 진화했다.

- **v1 (도메인 결합형)**: 위 다섯 번의 시도를 거쳐 문제지 에디터 내부에 하드코딩된 원형.
- **v2 (범용 엔진화)**: 임의의 콘텐츠로 일반화했으나, 210줄짜리 god-hook에 모든 책임이 엉켜 있던 구조.
- **v3 (독립 오픈소스 `column-pager`)**: 앱에서 완전히 분리해 **순수 코어 수학(Math) / DOM 측정 어댑터 / React 렌더러**의 3계층 클린 아키텍처로 재설계. 검증된 자산인 크롭 수학은 무결하게 보존하고 구조만 새로 짰다.

```tsx
<ColumnPager columnCount={2} pageHeight={1123} showDividers tightFill
  onPagesGenerated={(pages, html) => {/* 서버로 넘겨 PDF 변환 */}}>
  <ColumnPager.PageBreak />
  {items.map((it) => (
    it.isAtomic ? (
      <ColumnPager.KeepTogether key={it.id}>
        <ProblemTable {...it} />
      </ColumnPager.KeepTogether>
    ) : (
      <Problem key={it.id} {...it} />
    )
  ))}
</ColumnPager>
```

### 서브픽셀 트랩과 v1.1 고급 알고리즘
- **서브픽셀 렌더링 오차 방어**: 브라우저 줌이나 폰트 렌더링에 의해 `2090 / 697 = 2.998`처럼 소수점 오차가 생길 때, `Math.floor`를 쓰면 마지막 컬럼이 통째로 증발한다. 정수 N배여야 하는 값에는 반올림(`Math.round`)과 서브픽셀 허용 오차(Tolerance)를 적용했다.
- **원자적 블록 격리 (`KeepTogether`)**: 표나 차트처럼 중간에서 쪼개지 않고 통째로 다음 열로 넘겨야 하는 요소를 선언적으로 감싸는 `<ColumnPager.KeepTogether>` (`break-inside: avoid` 메커니즘) 구현.
- **밀집 패킹 (`tightFill`)**: 경계 요소의 텍스트를 정밀하게 분할해 이전 컬럼의 자투리 빈 공간을 빈틈없이 채우는 알고리즘 추가.
- **제로 의존성 레이아웃 애니메이션**: framer-motion 같은 무거운 외부 라이브러리 없이 `renderItem`과 `clipOverflow` 래퍼만을 노출하여, 안정적인 key 추적 기반으로 이동 중 잘림 없는 가벼운 애니메이션 지원.

## 결과

- **환불 문의 일 4건 → 주 2건 이하 격감**: 주력 서비스에서 2년 가까이 이어지던 인쇄 불량 및 지문 잘림 이슈를 완전히 뿌리뽑았다.
- **더블 레이어 테스트 검증**: 레이아웃에 독립적인 순수 코어 분할 알고리즘은 **결정적 단위 테스트 49개**로 단단히 고정하고, 실제 브라우저 렌더링은 **Storybook 13개 시각 스토리**로 회귀를 방어했다.
- **오픈소스 패키지 배포**: 임의의 React 노드를 고정 높이 페이지로 나누는 독립 패키지(`column-pager`, npm · MIT)로 배포하고, `semantic-release`로 main 브랜치 머지 시 버전 태깅과 CHANGELOG 작성을 자동화했다.

## 회고

처음 챕터 리드가 "모두가 실패했으니 부담 갖지 말라"며 건넸던 과제와 `column-count` 실패 힌트는, 결국 내게 **실패한 시도를 피하는 것이 아니라 그 실패의 본질을 분해해 창의적으로 다시 조립하는 법**을 가르쳐 준 최고의 자산이 되었다.

진짜 성과는 새로운 무언가를 발명한 것이 아니라, **망했던 네 번의 시도들을 버리지 않고 각도를 틀어 다시 조립한 것**이었다.

1번에서 픽셀 자르기의 참사를 겪어보지 않았다면 줄바꿈을 브라우저 다단 엔진에 맡길 생각을 못 했을 것이고, 2번에서 전체 다단 렌더의 폭망을 겪지 않았다면 카드 단위 복제라는 묘수에 도달하지 못했다.

문제가 풀리지 않을 때 가장 필요한 것은 더 복잡한 라이브러리를 찾는 것이 아니라, **실패한 가설들이 남겨준 단서들을 낯선 각도로 다시 바라보는 집요함**이라는 것을 배웠다.
