300페이지짜리 두꺼운 수능 기출 교재 PDF를 업로드하면, 화면에는 무지개 바람개비가 돌며 브라우저 탭이 그대로 얼어붙었다.

페이지 한 장을 그리는 데 약 2초(2,132ms). 300장이면 단순히 계산해도 10분이 넘는다. 실제로 첫 조작이 가능해지기까지 걸리는 시간(TTI)은 무려 639,000ms, 즉 **10분 30초**였다.

작업자들은 화면에 뜨는 "페이지가 응답하지 않습니다" 경고창을 보며 멍하니 모니터를 바라봐야 했고, 심지어 대용량 PDF는 브라우저 힙 메모리 초과(OOM Crash, '앗, 이런!' 화면)로 탭이 뻗어버려 작업하던 내역이 증발하기 일쑤였다.

이것은 서버에서 PDF를 생성하는 작업이 아니라, 브라우저에서 교재 PDF의 각 페이지를 캔버스(Canvas)로 래스터라이징한 뒤 작업자가 문제 영역을 지정해 잘라내는 웹 에디터 도구였다. 페이지 수에 정비례해 앞단에 쌓이던 거대한 렌더링 비용을 반드시 걷어내야 했다.

## 문제 진단: Chrome DevTools로 런타임을 해부하다

사실 이전에도 무거운 이미지 연산 속도를 끌어올리기 위해 C++ 기반 컴퓨터 비전 알고리즘을 **WebAssembly**(Wasm)로 컴파일한 `OpenCV.js`를 도입하는 등 성능을 개선하려는 시도가 있었다.

하지만 Wasm 도입만으로는 렌더링 블락과 탭 다운을 막기에 역부족이었다:

1. **Wasm도 메인 스레드 위에서는 UI를 멈춘다**: 아무리 C++ 수준으로 연산 속도가 빨라도, 메인 스레드에서 수백 장의 고해상도 이미지를 순회하며 윤곽선을 검출하는 순간 이벤트 루프는 여전히 락이 걸린다.
2. **연산 이전의 '입력 렌더와 메모리 병목'**: OpenCV가 처리할 입력 이미지 자체를 만드는 `PDF.js` 캔버스 래스터라이징이 앞단에서 10분간 메인 스레드를 독점했고, JS 힙과 Wasm 메모리 사이에 수백 장의 거대 비트맵이 복제되며 V8 한도를 터뜨렸다.

결국 **어떤 빠른 엔진을 쓰느냐**(Wasm)보다 **메인 스레드의 실행 흐름과 메모리 수명주기를 어떻게 스케줄링하느냐**가 문제의 본질이었다. 막연한 추측 대신 크롬 개발자 도구(Chrome DevTools)를 열어 성능 병목과 메모리 누수의 실체를 정밀하게 프로파일링했다.

### 1. Performance 탭: 메인 스레드를 질식시킨 Long Task의 행렬
Performance 탭에서 300페이지 로딩 과정을 기록하자, CPU Flamechart 전체가 수초짜리 **Long Task**(빨간색 경고 블록)로 빽빽하게 채워져 있었다.

`PDF.js`가 `<canvas>`에 벡터와 글리프를 래스터라이징하는 연산을 `Promise.all`로 한 번에 몰아 실행하면서, 브라우저 메인 스레드가 100% 점유되어 UI 렌더링과 이벤트 루프가 10분 동안 완전히 사망해 있던 것이었다.

### 2. Memory 탭: 힙 스냅샷(Heap Snapshot)과 Retainer 트리 분석
더 심각한 문제는 메모리 누수였다. Memory 탭에서 여러 시점의 힙 스냅샷을 비교(Comparison)하고 객체 참조 트리(Retainer Tree)를 추적하자 두 가지 치명적인 누수 원인이 드러났다:

1. **거대 비트맵 버퍼의 상태 누적**: 작업자가 문제를 고화질로 잘라내야 했기에 `scale = 3 × dpr` 고해상도로 렌더링된 base64 DataURL 문자열들이 React State 배열에 통째로 묶여 가비지 컬렉션(GC)되지 않고 메모리를 수백 MB에서 1.5GB 이상 집어삼키고 있었다.
2. **`PDFPageProxy` 내부 자원 미해제**: 래스터가 끝난 뒤에도 PDF.js 내부의 페이지 객체, 폰트 캐시, 오퍼레이터 스트림이 메모리에 영구 보존되어 있었다. `page.cleanup()`이 호출되지 않아 Retained Size가 페이지 수에 비례해 무한정 불어나고 있었던 것이다.

```text
[DevTools 힙 분석 결과]
1. Canvas 비트맵 (scale=3×dpr) 300장 동시 유지 → V8 Heap 1.5GB 돌파
2. PDFPageProxy 인스턴스 300개 Retained → C++/Wasm 폰트 버퍼 미해제
```

## 해결: 1초의 심리학과 인터럽트 기반 우선순위 스케줄링

`page.cleanup()`으로 메모리 누수를 잡으면서 브라우저 탭이 터지는 치명적인 사고는 막아냈다. 하지만 300장에 달하는 수백 페이지 PDF 전체를 고수준의 래스터라이징과 이미지 연산에 태우는 것은, 물리적으로 여전히 수십 초에서 수 분에 달하는 긴 로딩 시간이 걸렸다.

여기서 UX와 인지심리학 관점의 중요한 사실을 떠올렸다. 인간이 시스템의 지연을 느끼지 않고 생각의 흐름을 이어갈 수 있는 인지적 한계 시간은 **1초 이내**(골든 타임)라는 연구 논문이 있다. 1초를 넘어가면 사용자는 대기 시간을 의식하기 시작하고 몰입이 깨진다.

수백 장 전체가 다 끝날 때까지 수십 초를 기다리게 만드는 것은 최악의 경험이었다. 사용자가 첫 인터랙션을 시작하는 순간을 무조건 이 **1초대 이내**로 열어주는 것이 가장 최선의 전략이라고 판단했다.

### 1. 전수 대기 방식의 폐기와 1페이지 우선 렌더
기존 방식의 가장 큰 맹점은 "단 1페이지를 보여주기 위해 300페이지가 전부 완료될 때까지 화면을 꽁꽁 막아두는 전수 완료(All-or-Nothing) 방식"이었다.

하지만 사용자는 수백 페이지를 한꺼번에 읽지 않는다. **지금 당장 눈앞에 띄워진 단 1페이지만 소비한다.**

1. **첫 페이지만 1.3초 만에 즉시 렌더**: 문서를 열면 지금 당장 작업자가 보아야 할 **1페이지만 즉시 계산 및 렌더링**(1,310ms)하여 화면을 열어준다. 작업자는 1초 만에 마우스로 문제 영역을 자르며 작업을 시작할 수 있다.
2. **백그라운드 2페이지 청크 큐**: 나머지 299페이지는 백그라운드에서 2페이지 청크 단위(`chunk(pageNumbers, 2)`)로 쪼개어 브라우저 유휴 시간에 순차적으로 미리 연산해 둔다.

### 2. CS에서 배운 인터럽트(Interrupt) 기반의 우선순위 제어
마침 컴퓨터 사이언스(CS)를 깊이 공부하며 운영체제의 **인터럽트**(Interrupt)와 **선점형 우선순위 스케줄링** 개념을 접했던 터라, "이 원리를 브라우저 렌더링 큐에 그대로 도입해보면 어떨까?"라는 아이디어가 번뜩였다.

만약 전체 100페이지 중 백그라운드 큐가 5페이지를 그리고 있을 때, 작업자가 슬라이더나 목록에서 **30번째 페이지를 클릭(포커싱)한다면?**

- 백그라운드에서 돌고 있던 순차 연산을 즉시 일시 정지(Interrupt)한다.
- **30번째 페이지부터 최우선**(Priority)으로 즉석 연산 및 렌더링하여 화면에 즉각 띄워준다.
- 30번째 페이지의 렌더링이 완료되면, 멈췄던 백그라운드 큐를 이어서(Resume) 나머지 페이지들을 다시 차례로 연산 처리한다.

```ts
// 1. 포커싱된 페이지(예: 30번째 페이지) 우선 연산 & 캐시 확인
let image = pageCache.get(focusedPage);
if (!image) {
  // 백그라운드 큐보다 우선하여, 포커싱된 페이지만 즉시 On-Demand 렌더링
  const page = await pdf.getPage(focusedPage);
  image = await getViewportImage(page, RENDER_IMAGE_QUALITY, true);
  page.cleanup();
  pageCache.set(focusedPage, image);
}

// 2. 백그라운드 청크 순차 렌더링 (유휴 시간 큐 처리)
for (const c of chunk(remainingPages, 2)) {
  // 사용자가 다른 페이지를 클릭하면 즉시 인터럽트되어 해당 페이지만 먼저 처리
  const results = await Promise.all(c.map((n) => makeImage(pdf, n)));
  setPageImages((prev) => [...prev, ...results]);
}
```

엘리베이터에 거울을 달아 시선을 사로잡으면 층이 올라가는 대기 시간이 사라지는 것처럼, 사용자는 수백 페이지짜리 대용량 PDF가 로딩 대기 없이 즉석에서 열리는 것처럼 느낀다. 실제로는 뒤에서 치밀한 인터럽트 청크 스케줄러가 돌아가고 있을 뿐이다.

## 해결 2: `page.cleanup()`으로 Peak 메모리를 O(1)로 바운딩

DevTools 프로파일링에서 밝혀낸 메모리 누수를 잡기 위해, 래스터 직후 `page.cleanup()`을 명시적으로 호출하도록 수정했다.

각 페이지의 캔버스 래스터가 끝나자마자 PDF.js 내부의 C++/WebAssembly 폰트 스트림과 오퍼레이터 버퍼를 즉시 해제함으로써, 순간 피크(Peak) 메모리가 전체 페이지 수 $N$에 비례하던 것을 청크 크기(2페이지분)인 **상수 O(1) 크기**로 강제 바운딩했다.

이 조치로 V8 힙 메모리 폭증이 완전히 억제되었고, 대용량 PDF를 아무리 열어도 브라우저 탭이 얼거나 꺼지는 현상이 사라졌다.

## 솔직한 시행착오: OpenCV 품질 다운 트레이드오프

"전체 페이지 자동 영역 선택" 기능을 최적화할 때 한 가지 큰 교훈을 얻었다.

페이지 이미지를 OpenCV로 넘겨 문제 경계선을 컴퓨터 비전으로 자동 크롭하는 기능이었는데, 메모리를 더 아끼겠다는 욕심에 이미지 렌더 품질을 `0.2`로 대폭 낮춰보았다.

하지만 저해상도로 인해 OpenCV 알고리즘이 글자와 여백 경계를 제대로 감지하지 못하고 엉뚱한 위치를 오인식하는 문제가 발생했다. 메모리 숫자는 줄었지만 기능의 정확도가 깨져버린 것이다.

결국 렌더 품질을 다시 `1.0` 정품질로 복구하고, 5페이지 단위 청크화와 `page.cleanup()`만으로 메모리 피크를 방어했다.

**메모리는 숫자로 바로 보이지만 정확도는 결과물을 들여다봐야 보인다.** 기능의 정확성을 훼손하는 최적화는 엔지니어링이 아니라는 뼈아픈 교훈을 얻은 순간이었다.

## 결과

- **첫 조작 시간(TTI) 488배 단축**: 300페이지 기준 639,000ms(10분 30초) 걸리던 첫 조작 대기 시간을 **1,310ms**(1.3초)로 단축했다.
- **탭 크래시(OOM) 0건 달성**: $O(1)$ 메모리 바운딩과 `page.cleanup()` 자원 해제를 통해 브라우저 탭 멈춤 및 메모리 초과 크래시를 완전히 소멸시켰다.
- **작업 생산성 4배 향상**: 대용량 교재에서 문제 추출 작업을 진행하는 현장 작업자들의 작업 속도가 4배 이상 빨라졌으며, "기다리지 않고 바로 작업할 수 있어 업무 피로도가 획기적으로 줄었다"는 현장 피드백을 받았다.

## 회고

성능 최적화의 핵심은 막연한 감이나 추측이 아니라, **개발자 도구(DevTools)가 보여주는 프로파일러 그래프와 힙 스냅샷의 숫자를 믿는 것**이다.

Performance 탭의 Flamechart에서 메인 스레드를 막고 있던 Long Task를 짚어냈고, Memory 탭의 Retainer 트리에서 `page.cleanup()` 누락이라는 결정적 원인을 찾아낼 수 있었다. 동시에 "엘리베이터 거울"처럼 사용자의 심리와 체감 속도를 고려한 UX 설계가 결합되었을 때, 10분의 물리적 한계를 1초의 쾌적함으로 바꿀 수 있다는 것을 배웠다.

이번 최적화에서는 `page.cleanup()`을 통한 메모리 상수화와 2페이지 청크 스케줄링만으로도 메인 스레드의 숨통을 틔워 목표 성능을 충분히 달성할 수 있었다. 만약 페이지 수가 수천 장으로 늘어나거나 OpenCV 이미지 연산 자체가 프레임 예산(16ms)을 초과하는 수준이었다면, **다음 단계로는 Web Worker와 `OffscreenCanvas`를 도입해 래스터라이징과 Wasm 연산 파이프라인 전체를 백그라운드 스레드로 완전히 격리하는 아키텍처**를 적용했을 것이다.

불필요한 오버엔지니어링을 경계하면서도, 시스템의 한계와 다음 확장 카드가 무엇인지 명확히 쥐고 개발하는 것의 중요성을 배운 소중한 경험이었다.
