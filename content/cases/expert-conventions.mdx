새로운 교육 콘텐츠 제작 스튜디오 프로젝트에 합류했다. 첫날 내가 날린 첫 커밋은 비즈니스 기능 코드가 아니라 **ESLint와 Prettier 기반의 개발 표준 설정**이었다.

프로젝트를 열어보았을 때 마주한 현실은 충격적이었다. 8명의 개발자가 협업하는 거대한 프로젝트의 `.eslintrc.json`은 고작 단 한 줄뿐이었다:

```json
{ "extends": "next/core-web-vitals" }
```

Next.js 보일러플레이트가 깔아준 기본 설정이 전부였다. 포맷팅 룰도, import 정렬 규칙도, 커밋 전 타입 검사 게이트도 없었다. 상태 관리는 XState와 Zustand가 혼재되어 있었고, 스타일링은 MUI(Emotion)와 Tailwind가 어지럽게 뒤섞여 있었다.

여러 프리랜서와 사내 개발자가 거쳐 가며 손을 댈 때마다 각자의 코딩 스타일이 파편화되어 쌓였고, 이는 매일같이 팀의 귀중한 시간을 갉아먹는 보이지 않는 비용이 되고 있었다.

## 1. 보이지 않는 비용: 코드리뷰 피로와 인지 부하

비용은 두 곳에서 매일 새어나가고 있었다:

1. **비생산적인 코드리뷰**: 규칙이 없으니 PR마다 import 순서, 세미콜론, 들여쓰기 차이로 불필요한 diff가 쏟아졌다. 리뷰어는 정작 중요한 비즈니스 로직 대신 "여기는 카멜케이스", "import 순서 정리해주세요" 같은 사소한 스타일에 에너지를 소모했다.
2. **높은 인지 부하(Cognitive Load)**: 어떤 화면은 거대한 XState 상태 머신으로, 어떤 화면은 Zustand로 짜여 있어, 동료의 코드를 읽을 때마다 매번 새로운 사고방식에 적응해야 했다.

프로젝트의 뼈대를 밑바닥부터 다시 세우기로 결심했다.

## 2. 상태 관리의 대전환: XState를 걷어내고 '도메인 분할 Zustand'로

가장 큰 변화는 상태 관리 아키텍처의 단순화였다.

XState는 상태 전이를 엄격히 제어할 수 있지만 러닝커브가 매우 높았고, 단순한 UI 상태 하나를 추가하는 데도 수많은 보일러플레이트를 작성해야 했다. 개발자 경험(DX)과 온보딩 속도를 위해 `@xstate/react`와 `xstate` 의존성을 전면 걷어내고 **Zustand로 통일**했다.

핵심은 "거대한 하나의 스토어로 뭉치지 않는 것"이었다. 거대 스토어는 이름만 바뀐 또 다른 복잡성의 괴물이 될 뿐이었다.

기능(Feature) 단위, 그리고 관심사 단위로 **책임이 분명한 작고 납작한 단위의 스토어들로 잘게 쪼갰다**:
- 변형문제 기능: `configure`(설정), `edit`(편집), `passage-selection`(지문 선택), `tooltip` 스토어로 분할
- 문서 렌더러: `pages`, `action`, `header`, `references` 스토어로 분할

```ts
// 도메인별·관심사별로 쪼갠 작은 Zustand 스토어
export const useVariantQuestionConfigureStore = create<VariantConfigureStore>((set) => ({
  ...INITIAL_STATE,
  setVariantQuestionCount: (count) => set({ variantQuestionCount: count }),
  setIsIncludeExternalPassage: (value) => set({ isIncludeExternalPassage: value }),
  reset: () => set(INITIAL_STATE),
}));
```

각 스토어는 자신의 상태와 setter, 그리고 초기화(`reset`) 액션만을 지닌다. 기능이 커져도 스토어가 비대해지는 대신 개수가 늘어날 뿐이므로, 다음 사람이 필요한 스토어 파일만 열어보면 직관적으로 파악할 수 있는 구조를 완성했다.

## 3. 기계가 강제하는 컨벤션과 Git 게이트

"규칙을 지켜주세요"라는 사람의 주의력에 의존하는 컨벤션은 반드시 깨진다. 규칙은 기계가 강제해야 한다:

1. **엄격한 린트 & 포맷 룰셋**:
   - `import/order`: 내장 모듈 → 외부 패키지 → 내부 절대경로(`@/`) → 상대경로 순으로 정렬 강제.
   - `react/function-component-definition`: 컴포넌트는 화살표 함수로 통일.
   - `unused-imports`: 미사용 변수/임포트는 에러로 차단하되, `_` 접두사 변수만 의도적 예외로 허용.
   - Prettier + `prettier-plugin-tailwindcss`: 클래스 순서 자동 정렬.
2. **파일 네이밍의 합리적 절충**:
   처음에는 모든 파일을 케밥케이스로 통일하려 했으나, 리액트 생태계의 암묵적 상식인 **UpperPascalCase 컴포넌트 네이밍**(`ConfirmDialog.tsx`)으로 되돌렸다. 컨벤션은 개인의 신념보다 팀원 모두의 머릿속에 있는 보편적 상식에 맞출 때 마찰이 가장 적었다.
3. **Husky 기반의 Git 게이트 구축**:

```bash
# .husky/pre-commit — 변경된 파일만 린트 및 타입 검사
pnpm lint-staged
pnpm type-check

# .husky/pre-push — 단위 테스트 통과 시에만 푸시 허용
pnpm test --run
```

여기에 3종 PR 템플릿(기본, 핫픽스, 버그)과 `CODEOWNERS`를 도입하여, 리뷰어가 PR의 의도를 즉시 파악하고 담당자가 자동 배정되도록 자동화했다.

## 4. UI 및 스타일링 아키텍처 정리

- **Tailwind 유틸리티 통일**: MUI의 런타임 CSS-in-JS(`styled`, `sx`)를 완전히 걷어내고 Tailwind CSS로 통일하여 빌드 타임 스타일링과 런타임 제로 오버헤드를 확보했다.
- **Radix UI 헤드리스 컴포넌트 채택**: 무거운 완성형 UI 프레임워크에 기대는 대신, 접근성(a11y)과 키보드 인터랙션은 Radix 프리미티브에서 빌려오고 시각 디자인은 Tailwind와 CVA로 팀이 온전히 통제하는 원칙을 확립했다.
- **Sentry 에러 모니터링 연동**: React Query와 결합하여 배포 환경에서 발생하는 API 실패 및 렌더링 런타임 에러를 실시간으로 추적할 수 있는 관측 가능성(Observability)을 마련했다.

## 결과

* **코드리뷰 효율 극대화**: 포맷팅과 import 순서 같은 사소한 지적이 0건으로 사라지고, 코드리뷰의 초점이 순수한 비즈니스 로직과 아키텍처로 온전히 이동했다.
* **전사 프론트엔드 표준으로의 확산**: 스튜디오에서 확립된 **"Git 훅 강제 + 도메인 분할 Zustand + Radix/Tailwind + PascalCase 컴포넌트"** 골격은 사내 다른 형제 프론트엔드 서비스(디자인 시스템, 신규 제작 도구 등) 전반으로 전파되어 전사 표준 개발 환경으로 자리 잡았다.

## 회고: 컨벤션의 본질은 룰의 내용보다 '도입하는 방식'에 있다

이 프로젝트에서 얻은 가장 성숙한 배움은, 컨벤션을 세울 때 가장 중요한 것은 룰의 엄격함이 아니라 **그것을 팀에 도입하는 방식과 설득의 과정**이라는 점이었다.

처음에는 "이 룰이 맞다"는 확신으로 수백 개 파일의 포맷팅을 한 번에 갈아엎는 거대한 PR을 올렸다가, 동료들의 진행 중인 작업들과 충돌을 일으켜 당일 롤백되는 쓰라린 경험을 겪었다.

아무리 옳은 규칙이라도 팀의 호흡을 무시하고 한 번에 덮치면 배척당한다. 별도의 베이스 브랜치에서 변경을 단계적으로 조율하고, 동료와 리팩토링 범위를 나누어 점진적으로 적용했을 때 비로소 컨벤션이 팀의 진짜 자산으로 뿌리내릴 수 있었다.

컨벤션은 문서로 선언하는 것이 아니라 **도구와 구조로 강제될 때만 유지되며, 혼자 밀어붙이는 것이 아니라 팀과 호흡을 맞출 때 영속한다**는 값진 진리를 배운 프로젝트였다.
