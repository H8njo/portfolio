{/* NDA 안전: 사내 디자인 시스템. */}

사내 디자인 시스템을 맡았다. 처음엔 컴포넌트만 예쁘게 잘 만들면 되는 줄 알았다.

막상 해보니 일의 절반은 그게 아니었다. 컴포넌트를 잘 만드는 것과, **다음 사람이 그 위에서 실수 없이 일할 수 있도록 안전장치를 깔아두는 것**은 완전히 다른 차원의 일이었다. 디자인 시스템에서 컨벤션 하나를 잘못 정하면 그 실수가 수십 개의 서비스 프로젝트로 고스란히 복제되기 때문에, 사소한 인터페이스 하나도 가볍게 넘길 수 없었다.

버튼, 타이포그래피, 폼 입력, 탭 같은 기본 컴포넌트를 만드는 건 크게 막히지 않았다. Radix UI로 웹 접근성(a11y)을 탄탄하게 깔고, Tailwind CSS와 CVA(Class Variance Authority)로 variant를 정돈하며, Storybook에 문서를 붙이는 작업은 손에 익은 흐름이었다.

그렇다고 고민이 없었던 것은 아니다. 초기 Button 컴포넌트에는 욕심을 부려 비동기 핸들러가 오래 걸리면 로딩 스피너를 알아서 켜주는 마법을 넣었다가, "상태의 제어권을 쓰는 사람에게서 빼앗아 온다"는 치명적인 결함을 깨닫고 즉시 철회하기도 했다. 기본 컴포넌트에서는 화려한 마법보다 예측 가능한 동작이 언제나 우선이었다.

이런 소소한 의사결정 속에서, **가장 깊게 붙들려 치열하게 풀어낸 난제는 두 가지**였다:
1. 하나만 고르기와 여러 개 고르기를 단일 API로 합친 **Select 컴포넌트**
2. 사람의 개입 없이 컨벤션과 문서를 기계적으로 강제하는 **Plop 기반 코드젠 자동화 파이프라인**

## 첫 번째 — Select: 단일 API, 이중 엔진

드롭다운에서 **하나만 고르는 것**(예: 국가 선택)과 **여러 개 고르는 것**(예: 다중 태그 선택)은 사용하는 개발자 눈에는 똑같은 '선택 상자'처럼 보인다. 하지만 내부에서 동작하는 메커니즘은 완전히 다르다.

기존 `Select`는 단일 선택 부품(Radix Select) 위에 다중 선택을 억지로 흉내 내고 있었다. 그러다 보니 컴포넌트 내부에서 현재 무엇이 선택되었는지 정합성을 추적하지 못했고, 스크린리더가 읽어줄 선택 상태나 키보드 포커스 이동도 지원하지 못하는 '눈속임'에 불과했다.

억지로 한 몸에 우겨넣는 대신, **겉(소비하는 인터페이스)은 하나로 통일하고 속(엔진)은 둘로 완전히 분리**했다:
- **단일 선택**: Radix Select를 감싸 폼 연동과 접근성을 온전히 활용
- **다중 선택**: 별도 레이어 위에 선택 목록 상태 머신, 키보드 탐색, 체크박스 토글을 정밀하게 구현

여기에 TypeScript의 **상호 배타적 유니온**(Discriminated Union)으로 완벽한 컴파일 타임 안전장치를 걸었다:

```ts
type SelectV2SingleProps = CommonProps & {
  multiple?: false;
  value?: string;
  onValueChange?: (v: string) => void;
};

type SelectV2MultiProps = CommonProps & {
  multiple: true;
  value: string[];
  onValueChange: (v: string[]) => void;
};

export type SelectV2Props = SelectV2SingleProps | SelectV2MultiProps;
```

`multiple={true}`를 켜면 컴파일러가 `value`로 문자열 배열(`string[]`)을 강제하고, 끄면 단일 문자열(`string`)만을 허용한다. 타입을 잘못 쓰면 실행해 보기도 전에 IDE의 빨간 줄로 빌드가 차단된다.

### JavaScript 측정 없는 순수 CSS 자동 너비

드롭다운 트리거의 너비를 '목록 중 가장 긴 항목'에 맞추고 싶었지만, 항목들은 메뉴가 열리기 전에는 DOM에 렌더링되지 않아 크기를 측정할 수 없었다. 

이를 JavaScript의 `ResizeObserver`나 측정 루프 없이 **순수 CSS 복제본 트릭**으로 해결했다. 보이지 않는 숨김 복제본을 같은 그리드 셀에 겹쳐 두어 컨테이너가 가장 긴 항목 너비에 맞춰 저절로 늘어나게 만들고, 실제 보이는 버튼이 그 너비를 그대로 입도록 설계했다. 리사이즈 관찰 비용이나 불필요한 리렌더 루프를 0으로 만들었다.

## 두 번째 — Plop 자동화: 사람이 개입할 수 없는 구조적 컨벤션

디자인 시스템을 운영하며 겪은 또 다른 큰 병목은 **컴포넌트 스캐폴딩의 파편화**와 **수작업 아이콘 등록**이었다.

새 컴포넌트를 만들 때마다 개발자마다 폴더 구조가 미세하게 어긋나고 Storybook 문서가 누락되거나, 디자이너가 추가한 160여 개의 SVG 아이콘을 개발자가 손으로 하나하나 컴포넌트화하고 export 목록에 적어 넣는 방식은 휴먼 에러의 온상이었다.

이를 해결하기 위해 **Plop CLI 기반의 코드 생성 파이프라인**(`pnpm generate`)을 구축했다.

### 1. 컴포넌트 3-파일 자동 스캐폴딩 (`pnpm generate component`)

터미널에서 명령어 한 줄을 실행하고 컴포넌트 이름만 입력하면, 엄격한 컨벤션에 맞춰 **3개 파일 세트**를 즉시 생성한다:

```
src/components/<ComponentName>/
├── <ComponentName>.tsx          # CVA variant가 세팅된 기본 컴포넌트 뼈대
├── <ComponentName>.stories.tsx  # tags: ['autodocs'] 및 args/argTypes가 배선된 스토리
└── index.ts                     # 외부 공개용 배럴(barrel) export
```

- **PascalCase 정규식 검증**: `^[A-Z][A-Za-z0-9]*$` 정규식으로 프롬프트 단계에서 잘못된 네이밍을 차단.
- **Storybook Autodocs 사전 배선**: 스토리가 생성되자마자 Storybook에 문서와 인터랙티브 컨트롤이 자동으로 완성되도록 템플릿화하여 문서 누락을 방지.

### 2. 아이콘 자동화: 파일시스템을 단일 진실 공급원으로 (`pnpm generate icon`)

아이콘은 디자이너와 개발자의 커뮤니케이션 비용을 0으로 만드는 데 집중했다.

```
Figma SVG Export  →  assets/icons/design-system/*.svg  →  pnpm generate icon  →  index.ts (barrel) 자동 덮어쓰기
```

디자이너가 Figma에서 정해진 폴더에 SVG를 드롭하고 `pnpm generate icon`을 실행하면, Plop의 비동기 파일시스템 스캐너가 폴더를 읽어 **TypeScript 배럴(`index.ts`)과 타입을 통째로 재생성**한다.

```js
// .plop/plopfile.js — SVG 폴더를 스캔하여 배럴 파일을 완전 덮어쓰기
const files = await fs.promises.readdir(iconsDir);
const exports = files
  .filter((f) => f.endsWith('.svg'))
  .map((file) => {
    const name = file.replace(/\.svg$/, '');
    const pascal = name.charAt(0).toUpperCase() + name.slice(1);
    return `export { default as ${pascal} } from '../../assets/icons/design-system/${file}?react'`;
  });

// Spinner 등 특수 아이콘을 위한 escape hatch 병합
exports.push(`export * from './ExtraIcons'`);
await fs.promises.writeFile(outputFile, exports.join('\n') + '\n');
```

- **폴더가 곧 정답지**: 목록 파일을 사람이 손대지 않고 매번 새로 덮어쓰기 때문에, SVG 파일을 삭제하면 export 코드도 함께 사라진다.
- **`currentColor` 기반 테마 상속**: Figma 익스포트 프리셋 단계에서 색상을 `currentColor`로 고정하여, 아이콘별 라이트/다크 분기 코드 없이 부모의 CSS 글자색을 자동으로 상속받도록 처리.
- **Storybook 동적 갤러리 연동**: Storybook이 배럴(`import * as Icons from './index'`)을 통째로 순회하도록 작성하여, `generate` 한 번이면 스토리를 단 한 줄도 수정하지 않고도 신규 아이콘이 실시간 검색 및 테마 프리뷰 갤러리에 즉시 반영.

## 결과

* **Select**: 겉은 단순하지만 속은 완벽한 접근성과 상태 머신을 갖춘 1급 컴포넌트로 거듭났다. 복잡한 다단 트리 선택 상자나 탭이 결합된 드롭다운도 소비 제품 측에서 별도 스타일이나 상태 조작 없이 손쉽게 조립할 수 있게 되었다.
* **Plop & Storybook 자동화**: 새 컴포넌트 추가 시 컨벤션 드리프트가 0건으로 사라졌고, 아이콘 등록에 소요되던 수작업 커뮤니케이션이 완전히 증발했다. 디자이너가 SVG를 넣고 명령어를 치면 즉시 타입 안전한 컴포넌트와 Storybook 문서가 완성되는 자동화 워크플로우를 확립했다.

## 회고: 사람의 조심을 구조의 필연으로

컴포넌트를 하나 잘 만드는 것과, **동료들이 실수할 수 없도록 시스템을 깔아두는 것**은 완전히 다른 영역의 엔지니어링이었다.

시작할 때는 모두 "사람이 조심해서 쓰면 되는" 방식이었다. Select는 소비자가 개수를 직접 세서 상태를 넘겨야 했고, 아이콘과 컴포넌트는 누군가 수작업으로 파일을 만들고 목록에 한 줄씩 적어 넣어야 했다. 하지만 사람의 주의력에 의존하는 시스템은 서비스가 커질수록 반드시 균열이 발생한다.

Select에서는 **TypeScript의 타입 시스템**으로 잘못된 사용을 컴파일 타임에 막았고, 툴링에서는 **Plop과 파일시스템 기반 코드젠**으로 컨벤션과 문서를 기계적으로 강제했다.

디자인 시스템의 진정한 가치는 단순히 예쁜 UI를 제공하는 데 있지 않다. **"동료 개발자가 가장 직관적인 코드를 짰을 때, 그것이 가장 안전하고 올바른 결과물로 이어지도록 구조적 레일을 깔아주는 것."** 그것이 디자인 시스템 메인테이너로서 얻은 가장 큰 배움이었다.
