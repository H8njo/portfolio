교육 콘텐츠 제작 플랫폼을 개발했다. 작업자가 지문을 본문분석, 워크북, 변형문제 등의 형태로 편집하면, 이를 A4 다단 레이아웃으로 페이지를 분할하여 인쇄용 **PDF 교재**로 출력하는 핵심 시스템이었다.

그런데 이 PDF는, 실제로 파일을 다운로드해서 열어보기 전에는 화면이 제대로 렌더링되었는지 알 길이 전혀 없었다.

## 1. 문제: 렌더링을 확인하려면 매번 PDF를 내려받아야 했다

렌더링 결과가 의도대로 나왔는지 확인하는 방법은 오직 하나뿐이었다:
1. 백엔드에 PDF 생성을 요청한다.
2. 서버에서 무거운 다단 렌더링 작업이 끝나길 수십 초간 기다린다.
3. 생성된 PDF 파일을 로컬 컴퓨터로 다운로드하여 열어본다.

이 느리고 무거운 피드백 루프는 사내 여러 팀에 연쇄적인 병목을 일으켰다:

- **작업자의 깜깜이 불안감**: 에디터 화면에서 편집한 내용이 PDF에서도 완벽히 나올 것이라 믿고 다운로드하지만, 실제로는 다단 줄바꿈이나 폰트 렌더링 버그가 PDF 안에서 조용히 터져 있곤 했다.
- **디자인팀과 QA팀의 검수 지옥**: 교재마다 레이아웃과 폰트 크기가 제각각이라 모든 교재를 일일이 PDF로 뽑아봐야 했다. 하지만 한 권을 뽑는 데도 시간이 오래 걸려 전수 검사는 불가능에 가까웠고, 버그가 발생해도 "어떤 교재의 어느 옵션에서 터졌는지" 재현 조건을 좁히기가 극히 어려웠다.
- **개발자의 원인 추적 한계**: "PDF가 깨져요"라는 버그 리포트가 올라와도, 렌더링이 백엔드 헤드리스 브라우저에서 돌며 HTML을 생성하는 구조였기에 중간 렌더링 상태를 눈으로 확인할 수 없었다. 값을 실시간으로 바꿔가며 엣지 케이스를 테스트하기가 불가능했다.

결과물도, 그 중간 과정도 확인하려면 매번 무거운 생성 파이프라인을 통째로 돌려야만 했다. 그것이 테스트와 디버깅의 속도를 가로막는 근본 원인이었다.

## 2. 발상의 전환: PDF 엔진으로 화면에 렌더만 하고 멈추다

문제를 해결할 핵심 실마리를 잡았다:
**"PDF는 결국 브라우저에서 그린 다단 레이아웃 화면을 그대로 굳혀낸 것이다."**

그렇다면 **실제 PDF 생성에 사용되는 바로 그 페이지네이션 엔진(`AnalysisPager` 등)을 그대로 가져와 브라우저에 렌더링만 시키고 멈춘다면**, 무거운 다운로드 과정 없이도 실제 PDF와 100% 동일한 결과물을 실시간으로 볼 수 있지 않을까?

로드맵에는 없었지만, 이 병목을 깨기 위해 `/pdf-playground`라는 별도의 내부 개발용 놀이터 라우트를 자발적으로 구축했다.

```tsx
// pdf-playground: 실제 PDF 생성 엔진을 그대로 화면에 렌더링
<ErrorBoundary key={pagerKey} onReset={handleReset}>
  <AnalysisPager
    data={effectiveData}
    onPagesGenerated={(_, htmlString) => {
      // 이 HTML이 곧 실제 PDF가 되는 원본. 화면에 그대로 보존하여 즉시 확인.
      htmlStringRef.current = htmlString;
    }}
  />
</ErrorBoundary>
```

화면 구조는 명확하게 3단으로 구성했다:
- **왼쪽**: 실시간 JSON 핫 에디터 (데이터 즉시 수정)
- **가운데**: 실제 PDF로 출력될 다단 레이아웃 실시간 렌더러
- **오른쪽**: 교재, 단원, 지문, 분석 유형별 세부 옵션 컨트롤러

## 3. 세 팀의 페르소나를 녹여낸 4가지 생산성 장치

단순히 나 혼자 쓸 디버깅 도구가 아니라, 디자인팀, QA팀, 데이터관리팀이 각자의 목적에 맞게 자유롭게 쓸 수 있도록 4가지 장치를 심었다:

1. **타입별 맞춤형 실시간 렌더링**:
   본문분석(전문/한줄해석/좌우해석), 워크북, 변형문제 등 교재의 유형에 따라 오른쪽 패널의 설정 옵션이 유연하게 전환된다. 단원별·지문별 필터를 통해 검수하려는 지점을 정확히 집어내어 1초 만에 화면에 띄울 수 있다.

2. **JSON 실시간 핫 에디터 (엣지 케이스 재현)**:
   왼쪽 패널에서 렌더링에 주입되는 원본 데이터를 JSON으로 즉석 수정할 수 있다. 실제 교재에 없는 극단적인 장문, 특수 기호, 빈 문자열 등을 손으로 넣어 "이럴 때 레이아웃이 터지는가?"를 즉각 검증한다. 파싱 에러 발생 시 상단에 에러 배너만 띄우고 직전의 정상 렌더링을 유지하여 작업 흐름이 끊기지 않게 했다.

3. **ErrorBoundary 기반의 에러 시각화**:
   페이지를 나누는 알고리즘 도중 런타임 에러가 발생하면, 조용히 깨진 PDF를 뱉는 대신 ErrorBoundary가 화면에 에러 메시지와 스택 트레이스를 즉각 렌더링한다. 버그 리포트가 막연한 추측이 아닌 명확한 증거 기반으로 바뀌었다.

4. **URL 기반 완벽한 재현성과 에디터 양방향 이동**:
   - **에디터와 놀이터의 즉시 전환**: 에디터 URL(`/handout/{교재}/{지문}`)의 앞부분만 `/pdf-playground`로 바꾸면 방금 편집하던 지문이 즉시 PDF 렌더링 화면으로 열린다.
   - **링크 하나로 버그 100% 재현**: 선택한 교재, 단원, 지문, 분석 옵션 등 **모든 설정값이 실시간으로 URL 쿼리에 동기화**된다. QA나 디자인팀이 버그를 발견했을 때 장황한 캡처 설명 대신 **URL 링크 하나만 던지면 개발자 화면에서 그 상태 그대로 100% 재현**된다.

## 4. 결과: 전사 표준 검수 도구로의 승격

* **피드백 루프의 단축 (수십 초 → 0초)**: PDF 생성 및 다운로드 없이 화면에서 실시간으로 페이지 분할과 다단 레이아웃을 검증할 수 있게 되었다.
* **불필요한 서버 부하 급감**: 단순 확인을 위해 무수히 발생하던 백엔드 PDF 렌더링 생성 API 트래픽이 획기적으로 감소했다.
* **전사 협업 생산성 혁신**: 렌더링 버그 대응, 신규 에디터 기능 개발, 교재 디자인 검수 등 모든 관련 업무에서 "일단 플레이그라운드에서 확인하자"가 전사의 표준 워크플로우로 자리 잡았다.

## 5. 회고: 나무가 아닌 숲을 보며 만든 도구의 힘

가장 깊게 깨달은 점은, 개발의 진짜 병목이 기능 구현 자체가 아니라 **결과를 눈으로 확인하고 검증하는 피드백 비용**에 있었다는 사실이다.

렌더링 로직 자체는 훌륭했지만, 그것을 확인하기 위해 매번 무거운 파이프라인을 통째로 돌려야 했기에 모두가 고통받고 있었다. 실제 PDF 엔진을 브라우저 렌더러로 전환한 발상의 전환 하나로 그 비용을 0에 가깝게 줄일 수 있었다.

처음에는 사전 공유 없이 임의로 만든 페이지라 조심스러웠다. "제 디버깅용으로 만든 페이지인데 유용해 보여 공유드립니다. 스테이징에서만 쓰시고 필요 없으시면 프로덕션에선 빼겠습니다"라고 조심스럽게 팀에 전달했다.

하지만 반응은 폭발적이었다. 기능을 빼기는커녕, 디자인팀, QA팀, 데이터팀 모두가 프로덕션 환경에서도 필수적인 검수 및 미리보기 도구로 상시 활용하기 시작했다.

나 혼자의 디버깅 편의에 머무르지 않고, **동료들이 겪는 병목(숲)을 관찰하고 그들의 페르소나에 맞춰 만든 자발적 내부 도구**가 전사 조직의 속도를 얼마나 극적으로 끌어올릴 수 있는지를 온몸으로 체험한 뜻깊은 프로젝트였다.
