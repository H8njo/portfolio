비즈니스의 빠른 출시를 위해 3단계 위저드(Wizard)로 냈던 주문제작 기능을, 전사 공통 결제 시스템과 통합하기 위해 단일 폼으로 완전히 갈아엎었다.

교육 콘텐츠 마켓의 **주문제작 도서(Print-On-Demand, POD) 기능**이었다. 강사가 제작한 교재 PDF를 업로드하면 내지 컬러, 제본 방식(스프링/무선), 표지 코팅, 수량을 선택하여 실물 교재로 인쇄·배송받는 핵심 커머스 기능이었다.

인쇄 단가는 `페이지 수 × 컬러 단가 + 제본 단가` 공식으로 실시간 계산되어야 했기에, PDF를 올리자마자 1초 만에 페이지 수를 알아내어 견적을 보여주어야 했다.

## 1. 초기 설계와 빠른 출시: 3단계 위저드와 클라이언트 PDF 파싱

초기 출시 당시에는 비즈니스 검증이 최우선이었기에 **3단계 위저드 폼**(옵션 선택 → 배송지 입력 → 결제)으로 빠르게 파이프라인을 구축했다:

- **서버 왕복 없는 클라이언트 PDF 파싱**: 대용량 PDF를 서버로 올려서 페이지 수를 세면 네트워크 지연과 서버 부하가 발생한다. 브라우저에서 `pdf.js`로 PDF를 직접 파싱하여 0.1초 만에 페이지 수를 추출하고 파일 손상 여부까지 즉각 검증했다.
- **S3 Pre-signed URL 브라우저 직전송**: 파일 업로드 시 백엔드 서버를 중계기로 쓰지 않고, S3 임시 서명 URL을 발급받아 브라우저가 AWS S3로 바이너리를 직접 쏘아 서버 네트워크 대역폭을 아꼈다.
- **Context API 기반의 페이지 스코프 상태 격리**: 주문 프로세스를 벗어나면 버려져야 하는 일회성 상태였기에 전역 스토어를 더럽히지 않고 React Context로 상태 수명주기를 관리했다.

## 2. 통합의 벽: 전사 공통 결제 인프라와의 결합

위저드 폼으로 빠른 시장 출시에 성공했지만, 곧 거대한 아키텍처적 한계에 부딪혔다.

회사에는 이미 장바구니, 쿠폰 할인, 포인트 결제, 정기 구독이 유기적으로 연동된 **전사 공통 결제 퍼널 인프라**가 존재했다. 하지만 POD 위저드가 자체 결제 스텝을 독자적으로 품고 있었기에, 유저가 일반 교재와 주문제작 교재를 한 번에 묶어서 결제하거나 사내 할인 쿠폰을 적용할 수 없는 파편화가 발생했다.

결단을 내렸다: **"독자적인 위저드 결제 스텝을 완전히 떼어내고, POD 페이지를 '옵션 선택 후 장바구니로 담는' React Hook Form 기반의 단일 폼으로 전면 재설계한다."**

## 3. 리팩토링: 수동 DOM 조작에서 선언적 폼으로

위저드 시절 수백 줄의 코드로 손수 구현했던 기능들이 React Hook Form(RHF)으로 넘어가며 드라마틱하게 단순화되었다:

- **에러 포커스 자동화**: 이전에는 첫 번째 에러 필드로 스크롤시키기 위해 4개의 `ref`를 박고 `scrollIntoView()`를 돌렸으며, 숨겨진 파일 input에 포커스를 주려고 임시로 `display: block`을 줬다 빼는 기형적인 트릭을 썼다. RHF 전환 후 `shouldFocusError: true` 옵션 단 한 줄로 완벽히 대체되었다.

```tsx
const methods = useForm<PODForm>({
  mode: 'onTouched',
  shouldFocusError: true, // 수동 ref 4개와 scrollIntoView를 단 한 줄로 대체
  defaultValues: {
    color: '흑백',
    binding: '무선',
    quantity: 1,
  },
});
```

### 이탈 복원을 위한 `isLoaded` 듀얼 가드
비로그인 상태에서 복잡한 인쇄 옵션을 다 채워두고 "주문하기"를 눌렀을 때, 로그인 인증 리다이렉트를 거치며 페이지가 재마운트되어 입력값이 전부 날아가던 심각한 UX 결함이 있었다.

이를 `localStorage`에 자동 저장하고 복원하도록 개선했으나, 여기서 또 다른 동시성 버그가 발생했다:
1. 복원 `useEffect`가 실행되기 전에 변경 감지 `useEffect`가 빈 초기값으로 스토리지를 덮어써 버림.
2. 서버가 렌더링한 초기 빈 값과 클라이언트 복원값이 달라 Next.js SSR Hydration 불일치 에러 발생.

이를 **`isLoaded` 단 하나의 상태 플래그 가드**로 우아하게 해결했다:

```tsx
const [isLoaded, setIsLoaded] = useState(false);

// 1. 마운트 시 로컬스토리지에서 복원
useEffect(() => {
  const saved = localStorage.getItem('pod_draft_settings');
  if (saved) setSettings(JSON.parse(saved));
  setIsLoaded(true);
}, []);

// 2. 변경 시 저장 (복원 전 빈 값 덮어쓰기 원천 차단)
useEffect(() => {
  if (!isLoaded) return;
  localStorage.setItem('pod_draft_settings', JSON.stringify(settings));
}, [settings, isLoaded]);

// 3. 복원 완료 전까지 렌더링을 차단하여 Hydration 불일치 에러 방어
if (!isLoaded) return null;
```

## 결과

* **전사 커머스 생태계 통합**: POD 상품이 공통 장바구니 및 결제 시스템에 완벽히 통합되어, 복합 주문과 전사 프로모션 쿠폰 적용이 가능해졌다.
* **견고한 폼 복원 UX**: 사용자가 로그인이나 페이지 이탈을 겪더라도 작성 중이던 복잡한 인쇄 옵션이 100% 안전하게 복원되었다.
* **코드베이스 다이어트**: 수동 DOM 조작과 분기 로직이 RHF 표준 폼으로 전환되며 수백 줄의 레거시 코드가 삭제되었다.

## 회고: 빠른 출시의 도구와 통합의 도구는 다르다

처음에 위저드로 빠르게 출시했던 결정을 결코 후회하지 않는다. 빠른 시장 검증이 필요한 시점에는 위저드가 정답이었고, 서비스가 성장해 플랫폼과의 결합이 필요해진 시점에는 단일 폼 통합이 정답이었다.

**비즈니스의 생애 주기에 맞춰 아키텍처를 유연하게 진화시키는 것, 그리고 레거시를 두려워하지 않고 과감히 재설계할 수 있는 실행력**이 엔지니어링의 핵심임을 다시 한번 확인한 프로젝트였다.
