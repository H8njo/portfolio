평문 비밀번호나 민감한 사내 API 키가 프론트엔드 브라우저 코드 어딘가에 잠깐이라도 머무는 구조는 언제든 보안 사고로 이어질 수 있다.

사내 보안 위협 관리 및 관제 포털 시스템을 구축했다. 보안 분석가들이 이상 징후를 티켓 형태로 접수해 위협 IP나 악성 URL을 추적하고, 필요한 경우 방화벽 차단 정책을 즉시 실행하는 핵심 사내 시스템이었다. 나는 이 시스템에서 사용자 화면(Next.js)부터 그 뒤를 받치는 서버(NestJS)까지 프론트엔드와 백엔드를 아우르는 풀스택 개발을 맡았다.

## 문제: 브라우저는 신뢰할 수 없는 자리다

원래대로라면 브라우저 화면이 사내 코어 시스템의 내부 API를 직접 호출하도록 구현할 수도 있었다. 하지만 보안 시스템에서 이 방식은 치명적인 결함을 안고 있었다:

1. **브라우저는 누구나 열어보고 변조할 수 있는 공간이다.** 사용자가 개발자 도구를 켜서 코드를 디버깅하거나 네트워크 요청을 조작할 수 있다.
2. 클라이언트가 내부 API를 직접 부르는 순간, 인증 토큰을 브라우저에 노출해야 하고, 비밀번호 암호화 알고리즘이 화면 코드에 고스란히 드러나며, "이 사용자가 어디까지 볼 수 있는가"라는 접근 제어 권한 판단까지 프론트엔드가 떠안게 된다.

보안 시스템의 제1원칙은 **클라이언트에서 올라오는 모든 요청은 일단 신뢰할 수 없는 것으로 간주한다**는 것이다. 민감한 비즈니스 로직을 브라우저에 두면 의심하고 방어해야 할 보안 표면이 걷잡을 수 없이 넓어진다.

## 해결책: 브라우저와 코어 시스템 사이에 '경비실'을 세우다

방문객이 사내 금고에 직접 손을 댈 수 없도록, 방문객(브라우저)과 금고(내부 코어 API) 사이에 **단단한 경비실 역할을 하는 전용 중간 서버**를 한 겹 세웠다.

이를 아키텍처 용어로 **BFF**(Backend for Frontend)라고 부른다.

화면은 이제 내부 코어 API를 직접 알지 못하며, 오직 자신을 위해 특화된 BFF 서버하고만 통신한다. 신원을 검증하고, 데이터를 변환하며, 민감한 내부 시스템을 안전하게 제어하는 일은 모두 이 경비실이 도맡는다.

### 1. 보안에 민감한 로직은 전부 서버 뒤로 격리

- **비밀번호 해싱의 서버 전담**: 프론트엔드는 사용자가 입력한 비밀번호를 단순 전송하기만 하고, 내부 코어 시스템이 요구하는 암호화(SHA-256 해싱 및 솔트 처리)는 BFF가 내부에서 전담한다. 프론트엔드 코드는 해싱 알고리즘이 무엇인지조차 알 필요가 없다.
- **신원 사칭 원천 차단**: 티켓을 생성하거나 차단 명령을 내릴 때, 작성자 ID를 클라이언트 페이로드에서 받지 않는다. 사용자가 로그인할 때 발급된 **서버 측 세션(JWT 토큰)에서 직접 유저 식별자를 추출해 주입**한다. 클라이언트가 남의 ID로 요청을 위조할 틈새 자체를 없앴다.
- **데이터 열람 권한의 서버 강제**: 최고 분석관은 전체 티켓을, 일반 사용자는 자기 부서의 데이터만 열람해야 한다. 브라우저가 파라미터로 "전체 데이터 조회"를 요청하더라도, BFF가 세션의 권한 등급을 확인해 쿼리 조건을 서버 레벨에서 강제로 걸러낸다.

### 2. 10번의 산발적인 호출을 단 1번의 최적화된 응답으로 집계

대시보드 메인 화면 하나를 그리기 위해서는 수많은 정보가 필요했다:
- 내가 처리할 티켓 목록
- 전체 위협 등급 현황
- 보안 에이전트 설치율
- 실시간 IP/URL 차단 통계 지표

이 모든 것을 브라우저가 개별적으로 10여 번씩 호출하게 두면, 네트워크 왕복 지연(RTT)이 누적되어 화면 로딩이 눈에 띄게 느려진다.

BFF가 이 흩어진 호출들을 대신 삼켰다. 사내 고속 백엔드 네트워크망에서 `Promise.all`로 **10여 개의 내부 API를 병렬로 빠르게 집계한 뒤, 화면에 딱 맞게 정제된 단 1개의 DTO 응답으로 묶어 프론트엔드에 내려주었다.** 브라우저의 네트워크 비용이 획기적으로 줄어들었다.

### 3. 파일 스트리밍과 한글 인코딩 트러블슈팅

보안 로그 파일이나 첨부 문서를 주고받는 과정에서 발생하던 고질적인 문제들도 BFF 계층에서 깔끔하게 해결했다:

- **바이너리 파일 스트리밍 다운로드**: 대용량 로그 파일을 다운로드할 때 서버 메모리에 전체를 버퍼로 올리면 메모리 고갈(OOM)이 발생하거나 파일이 깨지기 쉽다. 내부 코어 시스템으로부터 들어오는 응답을 `StreamableFile` 파이프라인으로 연결해 브라우저로 막힘없이 스트리밍 중계했다.

```ts
// backend/src/tickets/attachments.controller.ts
@Post(':ticketId/attachments/:fileId/download')
async downloadAttachment(
  @Param('fileId') fileId: string,
  @Res({ passthrough: true }) res: Response,
) {
  const stream = await this.coreApiService.downloadFileStream(fileId);
  res.set({
    'Content-Type': 'application/octet-stream; charset=UTF-8',
    'Content-Disposition': `attachment; filename="${encodeURIComponent(stream.fileName)}"`,
  });
  return new StreamableFile(stream.data);
}
```

- **멀티파트 한글 파일명 인코딩 보정**: 파일 업로드 시 멀티파트 헤더의 한글 파일명이 `latin1(ISO-8859-1)`로 잘못 디코딩되어 깨지던 문제를, UTF-8 및 NFC 표준 정규화 변환 파이프라인을 거쳐 원본 파일명으로 온전하게 복원했다.

### 4. 데이터 성격에 맞춘 하이브리드 이중 DB (Dual Database)

하나의 서비스 안에서 다루는 데이터의 성격이 극단적으로 달랐기에, 무리하게 단일 DB에 모든 것을 담지 않고 **이중 데이터베이스 전략**을 취했다:

- **PostgreSQL (TypeORM)**: 사용자 계정, 권한 체계, 티켓 상태 머신 등 엄격한 트랜잭션과 관계 정합성이 필수적인 정형 데이터 관리.
- **MongoDB (Mongoose)**: 외부 위협 피드, 실시간 차단 로그, 알림 히스토리 등 데이터 구조가 유연하게 변하고 유입량이 많은 비정형 시계열 데이터 수집.

단일 NestJS 애플리케이션 안에서 두 DB 커넥션을 깔끔하게 주입받아 단일 비즈니스 플로우로 자연스럽게 엮어냈다.

## 결과

* **보안 경계의 단순화**: 프론트엔드는 암호화 로직, 사내 코어 API 토큰, 권한 검증, 인코딩 변환을 전혀 신경 쓸 필요가 없어졌다. 모든 보안 통제가 BFF 한곳에 집중되면서 보안 감사(Audit)와 취약점 점검을 수행할 때도 BFF 경계만 검증하면 되는 명확한 구조가 완성되었다.
* **사용자 경험(UX) 및 성능 극대화**: 10여 개에 달하던 대시보드 API 호출이 단 1회로 통합되어 초기 로딩 지연이 대폭 단축되었고, 대용량 바이너리 로그 파일도 깨짐 없이 안정적으로 스트리밍 다운로드할 수 있게 되었다.

## 회고: 풀스택 관점에서 바라본 보안과 책임의 경계

프론트엔드와 백엔드를 함께 개발하면서 얻은 가장 큰 자산은 **특정 비즈니스 로직이 아키텍처의 어느 계층에 위치해야 하는가**를 명확한 기준을 갖고 판단하는 감각이었다.

BFF를 도입하면 관리해야 할 서버가 한 겹 늘어나고 DTO 인터페이스를 양쪽에서 맞춰야 하는 개발 비용이 발생한다. 하지만 보안과 데이터 정합성이 최우선인 엔터프라이즈 시스템에서는, 이 '한 겹의 경비실'이 가져다주는 이점이 비용을 압도했다.

**신뢰할 수 없는 클라이언트의 영역**과 **검증된 비즈니스 로직이 수행되는 서버의 영역**을 물리적으로 명확히 가르고, 클라이언트는 가벼운 렌더링에만 집중하도록 만드는 것 — 그것이 풀스택 아키텍처가 제공할 수 있는 최고의 안정성이자 가치임을 체득한 프로젝트였다.
