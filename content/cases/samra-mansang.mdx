{/* 개인 사이드 프로젝트: 로스트아크 업적 최적화 플랫폼. */}

게임 하나에 달성해야 할 업적이 자그마치 2,222개나 있었다.

유저들은 이 방대한 업적을 관리하기 위해 커뮤니티에서 거대한 엑셀 스프레드시트를 서로 공유하며 수작업으로 체크하고 있었다. 하지만 게이머의 입장에서 늘 답답함이 남았다:

**"스프레드시트는 '내가 지금까지 뭘 깼는지'는 보여주지만, '그래서 목표 칭호를 따려면 다음에 무엇부터 깨는 게 가장 빠른지'는 알려주지 못한다."**

업적마다 주어지는 경험치 가중치가 다르고, 선행 해금 조건이 얽혀 있으며, 특정 던전을 돌면 여러 업적이 한꺼번에 깨지는 복합 시너지가 존재한다. 이것은 사람이 눈으로 풀 문제가 아니라 **그래프 최적화(Graph Optimization) 문제**였다.

누구도 만들어주지 않기에 직접 뛰어들었다. 프론트엔드(Next.js)부터 백엔드(NestJS + Prisma), 데이터 크롤링과 시딩까지 1인 풀스택으로 완성한 최적화 플랫폼 개발기다.

## 1. 문제: 추천은 단순 정렬이 아니고, 수동 체크는 아무도 안 쓴다

프로젝트를 설계하며 마주한 핵심 난관은 두 가지였다:

1. **경로 추천은 단순한 '경험치 내림차순 정렬'이 아니다**:
   2,222개의 업적은 10개 대분류, 50개 이상의 서브카테고리로 중첩되어 있고, 레어도(NORMAL 1,615개 / RARE 476개 / EPIC 131개), 소요 시간, 장비 레벨, 필요 재화가 AND/OR 복합 조건으로 얽혀 있었다. 단순히 경험치를 많이 주는 순으로 나열하는 것이 아니라, **"함께 동선이 겹쳐서 동시에 깨지는 업적 묶음"을 고려해 목표 경험치까지 최소 비용으로 도달하는 최적 경로**를 찾아야 했다.

2. **2,222개를 손으로 체크하라고 하면 아무도 쓰지 않는다**:
   진행 상황을 유저가 2,000번 클릭해서 체크해야 한다면 스프레드시트와 다를 바 없었다. 게임 화면을 인식해 진행 상황을 자동으로 동기화할 수단이 절실했다.

## 2. 데이터 소스의 한계: 공식 API와 OCR의 트레이드오프

로스트아크 공식 OpenAPI는 캐릭터 레벨이나 장비 정보는 정확하게 제공하지만, **개별 업적의 달성 여부 데이터는 API로 전혀 제공하지 않았다.**

선택지는 둘 중 하나였다:
- **선택 A**: 2,000개 체크박스를 유저가 직접 수작업으로 체크하게 한다.
- **선택 B**: 인게임 업적 화면 스크린샷을 업로드받아 **OCR(광학 문자 인식)로 읽어 자동 추출**한다.

OCR은 게임 폰트, 해상도, UI 테마에 따라 100% 완벽한 인식을 보장하기 어렵다. 하지만 '수작업 입력의 피로로 인해 아무도 쓰지 않는 서비스'가 되는 것이 훨씬 치명적이라고 판단했다.

결국 **부정확함을 감수하더라도 자동화를 택하고, OCR 결과를 유저가 한눈에 확인하고 교정할 수 있는 '검수 단계(Human-in-the-loop)'를 UI에 배치**했다. 100% 완벽하지 않은 자동화라도, 처음부터 2,000개를 손으로 치는 것보다는 압도적으로 빠르고 편리했다.

## 3. 핵심 엔지니어링 구현

### ① 묶음 시너지를 반영한 그래프 기반 최적 경로 알고리즘
업적을 노드로, 경험치와 소요 비용을 가중치로 모델링했다. 엄밀한 전역 탐색의 연산 비용을 줄이기 위해, "동일 던전/필드에서 함께 달성되는 업적 군집"에 높은 우선순위 가중치를 부여하는 그리디 기반의 묶음 추천 알고리즘을 구축했다. 유저의 플레이 패턴에 기반해 목표 칭호까지의 예상 달성 일자도 함께 계산했다.

### ② 비선형 진행을 담아내는 Prisma 스키마와 OCR 파이프라인
화면에서 추출된 텍스트를 2,222개 업적 DB와 퍼지 매칭(Fuzzy Matching)하여 진행도를 갱신했다. 특히 다단계 업적의 경우 1단계를 깨고 2단계를 건너뛴 뒤 3단계를 달성하는 비선형적 플레이가 발생할 수 있어, 단순 숫자 카운트가 아닌 정수 배열(`completedStages Int[]`) 형태로 스키마를 설계하여 데이터 무결성을 지켰다.

```prisma
model UserAchievement {
  status          String  // not_started / in_progress / completed
  currentStage    Int     // 하위 호환용
  completedStages Int[]   // 개별 완료 단계 인덱스 배열 — 비선형 진행 표현
  
  user            User        @relation(fields: [userId], references: [id])
  userId          String
  achievement     Achievement @relation(fields: [achievementId], references: [id])
  achievementId   String

  @@unique([userId, achievementId])
}
```

### ③ 208개 월드맵의 268MB 에셋을 10.7MB로 96% 다이어트
인게임 월드맵 208개 위에 수집품과 최적 동선을 렌더링하기 위해 Leaflet 기반의 인터랙티브 맵을 구축했다. 하지만 원본 맵 이미지 용량이 268MB에 달해 모바일 로딩이 불가능했다.

Sharp 이미지 처리 파이프라인을 구축하여 **256px 타일 단위로 조각내고 WebP로 압축 변환하여 전체 용량을 10.7MB**(약 96% 절감)로 깎아낸 뒤 Cloudflare R2 CDN으로 서빙했다.

또한 맵 컨테이너의 DOM 레이아웃 측정이 완료되기 전에 마커가 렌더링되어 좌표가 튀는 문제를 방지하기 위해, '지도 렌더 준비 완료' 상태 게이트를 두어 좌표 정합성을 완벽히 맞췄다.

## 결과

* **1인 풀스택 서비스 런칭**: 2,222개 업적 계층 DB, OCR 스크린샷 일괄 등록, 208개 인터랙티브 타일 맵, 최적 경로 추천 엔진이 하나로 맞물린 라이브 웹 서비스를 완성했다.
* **에셋 96% 절감**: 268MB의 거대한 월드맵 에셋을 10.7MB로 압축하여 저사양 모바일 기기에서도 부드러운 타일 맵 로딩을 달성했다.

## 회고

처음에는 OCR의 인식률을 100%로 끌어올리려는 욕심에 매달려 기능 출시를 미루곤 했다. 하지만 사용자의 '검수 단계'를 화면에 자연스럽게 배치하여 불완전함을 시스템으로 보완하자 비로소 서비스가 빛을 볼 수 있었다.

진짜 훌륭한 엔지니어링은 언제나 '기술 자체의 완벽함'에 머무는 것이 아니라, **현실의 불완전한 제약을 인정하고 사용자 경험(UX)과의 타협점을 찾아내어 실제로 굴러가는 제품을 만들어내는 용기**에 있다는 것을 깊이 체득한 프로젝트였다.
