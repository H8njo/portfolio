요즘 개발할 때 코드 작성의 상당 부분을 Claude Code 같은 AI CLI에게 맡긴다.

진짜 문제는 명령을 내린 직후에 발생했다. 걸리는 시간이 30초든 3분이든, 작업이 끝났나 싶어 자꾸 터미널을 들여다보게 되고, 브라우저를 열어 딴짓을 하다가도 "이제 됐나?" 싶어 `Cmd+Tab`을 쉴 새 없이 연타했다. 온전히 쉬는 것도 아니고 몰입해서 일하는 것도 아닌, 어정쩡한 주의 분산과 피로가 온종일 쌓여갔다.

"AI가 작업을 시작하면 알아서 브라우저나 유튜브로 화면을 넘겨주고, 작업이 끝나거나 내 입력이 필요해지면 자동으로 터미널로 화면을 불러와 주면 안 될까?"

시장을 찾아보았지만 "AI 기다리는 시간이 아깝다"는 불평만 많을 뿐, AI 작업 상태에 따라 애플리케이션 포커스를 자동으로 전환해 주는 도구는 어디에도 없었다.

"없으면 내가 직접 만든다." 그렇게 macOS 네이티브 유틸리티 **afk** 프로젝트가 시작되었다.

## 1. 웹 개발자가 Xcode 없이 Swift를 선택한 이유

메뉴바에 상주하며 OS 레벨에서 다른 애플리케이션의 윈도우 포커스를 제어하려면 운영체제 네이티브 권한이 필수적이었다.

Electron으로 감싸서 빠르게 만들 수도 있었지만, 백그라운드에서 조용히 떠 있어야 할 가벼운 메뉴바 유틸리티 하나에 100MB가 넘는 메모리를 낭비하는 것은 도저히 납득할 수 없었다. 그래서 **Swift와 SwiftUI 네이티브**로 직행하기로 결정했다.

문제는 내가 평생 웹만 개발해 온 프론트엔드 엔지니어라는 점, 그리고 **수십 기가바이트에 달하는 무거운 Xcode IDE를 설치하기가 너무나 싫었다는 점**이었다.

메뉴바 앱 하나 만들자고 거대한 IDE를 통째로 내려받는 대신, macOS Command Line Tools에 기본 내장된 **Swift Package Manager**(SPM)만으로 빌드 파이프라인을 구축할 수 있는지 검증했다:
- `swift build`로 컴파일하고
- 셸 스크립트(`bundle.sh`)로 `.app` 번들과 `Info.plist`를 직접 조립했으며
- 앱 아이콘과 메뉴바 씬은 SwiftUI의 `MenuBarExtra`와 `LSUIElement`(Dock 아이콘 숨김) 속성으로 제어했다.

IDE의 도움 없이 순수 CLI 터미널 환경만으로 완벽한 macOS 네이티브 앱을 빌드하고 패키징할 수 있음을 증명한 첫 번째 승리였다.

## 2. 셸 훅과 앱의 결합도 제로 통신: 파일시스템 관찰자

Claude Code에는 [Hooks](https://docs.anthropic.com/en/docs/claude-code/hooks) 기능이 있다. `UserPromptSubmit`, `Notification`, `Stop` 같은 이벤트가 발생할 때마다 지정된 셸 스크립트를 실행할 수 있다.

즉, "AI가 지금 무슨 일을 하고 있는지"를 셸은 실시간으로 안다. 핵심은 **이 셸 스크립트의 상태를 백그라운드에서 도는 Swift 앱으로 어떻게 넘기느냐**였다.

소켓(WebSocket)이나 로컬 HTTP 서버를 띄우는 방식도 검토했지만, 단순한 상태값 몇 개를 주고받자고 무거운 IPC 채널을 여는 것은 전형적인 오버엔지니어링이었다.

가장 단순하고 견고한 방식을 택했다. 바로 **파일시스템**(Filesystem)이었다.

```json
// ~/.afk/sessions/{session_id}.json
{
  "state": "working",
  "session_id": "e05d...",
  "prompt": "테스트 코드 작성해줘",
  "app": "Cursor",
  "app_bundle": "com.todesktop...",
  "ts": "2026-06-18T10:00:00Z"
}
```

- **결합도 0 (Zero Coupling)**: Claude Code는 afk의 존재를 전혀 모른다. 훅 스크립트는 상태가 바뀔 때마다 세션별 JSON 파일을 기록하고, afk 앱은 해당 디렉토리를 지켜보기만 한다.
- **원자적 파일 쓰기**: 불완전한 JSON 읽기(Race Condition)를 방지하기 위해, 임시 파일에 먼저 쓰고 `mv` 명령어로 원자적으로 바꿔치기(Atomic Swap)했다.
- **멀티 세션 우선순위 집계**: 터미널 창을 여러 개 띄워 다중 AI 세션이 돌 때, 앱의 `SessionMonitor`는 명확한 우선순위 규칙으로 상태를 하나로 집계한다:
  - 하나라도 `waiting_for_user`(사람 입력 대기) 상태면 **최우선 승리**
  - 그 외에는 `working`(작업 중)
  - 모든 세션이 완료되면 `idle`(대기)
- **화면 깜빡임 방지 디바운스**: `working` 상태로 바뀌면 2초의 전환 지연을 두었다. 이 지연이 없으면 AI와의 짧은 핑퐁 대화 중에 화면이 미친 듯이 깜빡이기 때문이다. 그사이에 상태가 다시 바뀌면 예약된 포커스 전환을 즉시 취소했다.

## 3. 가장 큰 난관: 미서명 앱(Unsigned App)이라는 거대한 벽

터미널 감지와 상태 집계까지는 순조로웠다. 진짜 복병은 **완료 알림 배너**에서 터졌다.

AI 작업이 끝나면 화면 우상단에 세련된 완료 배너를 띄우고 싶었다. 당연히 macOS의 공식 알림 API인 `UNUserNotificationCenter`를 호출하면 끝날 줄 알았다. 하지만 아무리 코드를 실행해도 알림은 화면에 단 한 번도 뜨지 않았다.

원인을 파고들다 마주한 진실은 충격적이었다. **Apple Developer 유료 인증서로 서명(Code Signing)되지 않은 앱은 macOS 시스템 알림 설정 목록에 아예 등록조차 되지 않는다.** 시스템 설정에 없으니 알림을 보낼 권한 자체가 영구 차단된 것이다.

- `osascript`로 시스템 알림을 띄우면? → 배너가 뜨지 않고 알림 센터 내부에만 조용히 박힌다.
- `NSPanel`을 띄우면? → `LSUIElement`(독 없는 백그라운드 앱) 구조에서는 화면에 표시되지 않는다.

세 번의 막다른 길 끝에 내린 결론은 **OS가 알림을 안 주면, 알림처럼 생긴 투명 윈도우를 직접 그린다**였다:

```swift
let window = NSWindow(
  contentRect: rect,
  styleMask: [.borderless],
  backing: .buffered,
  defer: false
)
window.level = .screenSaver                   // 모든 앱 및 풀스크린 위에 최상단 노출
window.backgroundColor = .clear
window.collectionBehavior = [.canJoinAllSpaces, .stationary]
window.contentView = NSHostingView(rootView: bannerView) // 내부는 세련된 SwiftUI 뷰
window.orderFrontRegardless()                 // 독 없는 백그라운드 앱에서도 강제 렌더링
```

테두리 없는 투명 `NSWindow`를 스크린세이버 레벨(`.screenSaver`)로 띄워 풀스크린 상태의 다른 앱 위에도 무조건 보이게 만들고, 그 위에 SwiftUI로 배너 UI를 얹었다. 여러 세션이 동시에 끝날 때 배너가 위아래로 자연스럽게 쌓이고 사라지도록 수직 스택 좌표 계산까지 손수 구현했다.

## 4. 디테일과 시행착오

1. **터미널 계층 구조 감지**: Cursor 에디터 내부 터미널에서 실행할 경우, 부모 프로세스로부터 상속받은 `TERM_PROGRAM=iTerm.app` 환경변수가 남아 엉뚱한 터미널로 포커스가 튀는 버그가 있었다. 이를 해결하기 위해 `CURSOR_CLI` → `VSCODE_PID` → `TERM_PROGRAM` 순으로 검증하는 계층적 우선순위 감지 로직을 구축했다.
2. **이상적인 상태 기계와 현실의 괴리**: 처음 설계한 상태 전이는 `working → waiting_for_user → idle`이었다. 하지만 실제 Claude Code는 작업 종료 시 `Notification`과 `Stop` 이벤트를 찰나의 순간에 연달아 쏘며 `working → idle`로 직행했다. 설계 다이어그램만 고집하지 않고, 실제 발생하는 이벤트 흐름에 맞춰 `idle` 전이 시점에서도 완료 알림과 포커스 전환이 유연하게 트리거되도록 상태 머신을 교정했다.

## 결과

* **Homebrew Cask 공식 배포**: `brew tap H8njo/tap && brew install --cask afk` 명령어 한 줄로 전 세계 누구나 설치할 수 있는 오픈소스 macOS 앱으로 배포했다. (저장소: `H8njo/afk`)
* **초경량 네이티브 UX**: 메모리 점유율 단 5MB 미만으로 상주하며, AI 작업 시작 시 브라우저 전환 → 완료 시 터미널 복귀 및 플로팅 배너 알림을 매끄럽게 수행하여 개발자의 인지 피로를 0으로 줄였다.

## 회고: 낯선 플랫폼의 진짜 장벽은 문법이 아니라 '암묵적인 룰'이다

새로운 언어나 플랫폼에 도전할 때 진짜로 시간을 잡아먹는 것은 Swift 같은 프로그래밍 언어의 문법이 아니었다. **"서명되지 않은 앱은 OS가 시스템 API를 걸어 잠근다"와 같은 플랫폼 고유의 암묵적인 보안 규칙과 샌드박스 정책**이 진짜 난관이었다.

하지만 막다른 길을 만날 때마다 좌절하는 대신, 윈도우 레벨을 조작해 커스텀 렌더링 윈도우를 띄우며 플랫폼의 제약을 정면으로 돌파했다.

동시에 셸 훅과 네이티브 앱 사이의 통신을 복잡한 IPC 대신 **'파일 한 장'이라는 가장 단순한 인터페이스로 연결한 설계**는 최고의 선택이었다. 터미널에서 `cat` 명령어로 세션 상태를 즉시 눈으로 디버깅할 수 있었기 때문이다.

웹에서 체득한 아키텍처 원칙 — **"가장 단순하고 결합도가 낮은 경계를 선택하라"** — 은 데스크톱 네이티브 생태계에서도 변함없이 강력하게 작동한다는 것을 확인한 즐거운 도전이었다.
