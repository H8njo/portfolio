커머스 홈 화면을 전면 개편할 때였다.

기존의 단조로운 홈을 배너, 퀵메뉴, 신규 구독 상품(패스 상품), 맞춤 교재 추천, 랭킹 등 다양한 모듈이 조립되는 모듈형 홈으로 다시 구성해야 했다. 비즈니스 요구사항은 빠르게 쏟아졌다: "패스 구독 상품은 가격 대신 '패스 이용 시 0원'이라고 떠야 해요", "할인율이 10% 이상일 때만 빨간 뱃지를 붙여주세요", "주문제작 도서는 배송비 안내 뱃지가 필요해요."

요구를 맞추다 보니, 가장 많이 쓰이는 도서 카드 컴포넌트(`BookCard`)가 순식간에 복잡한 괴물이 되어가고 있었다.

## 문제

컴포넌트 하나가 온 회사의 비즈니스 규칙을 다 알고 있었다.

처음에는 단순하게 접근했다. 각 섹션에서 필요한 prop을 카드에 하나씩 뚫었다:

```tsx
// AS-IS: 비즈니스 규칙이 컴포넌트 안에 하드코딩된 상태
<BookCard
  book={book}
  isSolvookPassOnly={isPass}
  isDiscounted={book.discountRate > 0.1}
  isCustomPrint={book.type === 'POD'}
/>
```

그리고 `BookCard` 안쪽은 온갖 삼항 연산자와 조건문으로 도배됐다:

```tsx
<PriceText>
  {isSolvookPassOnly
    ? '패스 이용 시 0원'
    : isCustomPrint
    ? `주문제작 ${formatPrice(book.price)}원`
    : `${formatPrice(book.discountPrice || book.price)}원`}
</PriceText>
```

이렇게 짜고 나니 즉시 부작용이 터졌다:
1. **재사용 불가**: 홈의 큐레이션에서는 잘 동작하던 카드가 검색 결과 목록이나 마이페이지에서는 비즈니스 규칙이 달라 깨졌다.
2. **사이드이펙트 폭탄**: 기획팀에서 "패스 문구를 '0원 패스'로 바꿔주세요"라고 요청하면, 프론트엔드 코드 여러 곳의 삼항 연산자를 찾아 수정하고 배포해야 했다.
3. **테스트 불가**: 컴포넌트를 테스트하려면 가능한 모든 비즈니스 조합의 boolean prop 플래그를 조합해 넘겨야 했다.

## 트레이드오프 결정

"프론트엔드 뷰 컴포넌트는 비즈니스 문구의 의미를 몰라야 한다."

컴포넌트가 도메인 지식을 많이 알수록 당장은 부모가 넘길 데이터가 적어 편해 보인다. 하지만 이는 결합도를 높이고 변경 비용을 프론트로 떠넘긴다.

결정을 내렸다. **`BookCard`에서 모든 비즈니스 분기를 걷어내고, 표시 책임을 완전히 데이터(서버 응답 모델)로 위임하여 컴포넌트를 '도메인 무지(Domain-Agnostic)' 상태로 만든다.**

프론트엔드가 자체적으로 가격을 계산하거나 문구를 조합하는 대신, 서버가 화면에 표시될 의도를 담은 데이터를 규격화하여 내려주도록 API 계약을 조정했다.

## 접근

### 1. 표시 책임을 유니온 데이터 모델로 위임
가격을 단순 숫자가 아닌 `number | string` 유니온으로 정의하고, 뱃지도 정해진 문자열 배열(`badgeText`)로 일원화했다:

```ts
interface BookDisplayItem {
  id: string;
  title: string;
  thumbnailUrl: string;
  price: number | string; // 15000 | "패스 이용 시 0원"
  originalPrice?: number;
  badgeText?: string;     // "BEST", "주문제작", "15% 할인"
}
```

이제 `BookCard`는 비즈니스 조건을 전혀 몰라도 된다. 숫자가 오면 쉼표 포맷팅을 하고, 문자열이 오면 그대로 그린다:

```tsx
// TO-BE: 순수한 도메인 무지(Presentation) 컴포넌트
export function BookCard({ title, thumbnailUrl, price, badgeText }: BookDisplayItem) {
  return (
    <CardContainer>
      {badgeText && <Badge>{badgeText}</Badge>}
      <Thumbnail src={thumbnailUrl} alt={title} />
      <Title>{title}</Title>
      <Price>{typeof price === 'number' ? `${price.toLocaleString()}원` : price}</Price>
    </CardContainer>
  );
}
```

이제 새로운 프로모션이나 가격 정책이 추가되어도 프론트엔드 코드를 한 줄도 건드리지 않고 서버 데이터 변경만으로 즉시 대응할 수 있게 됐다.

### 2. 레이아웃과 간격 책임의 일원화
컴포넌트 외형뿐 아니라 레이아웃 구조에서도 책임 분리가 중요했다.

- **Full-bleed 뷰포트 배경**: 전체 회색 배경 위에 가운데 정렬된 컨테이너(max-width: 1200px)를 유지하면서 특정 흰색 섹션만 화면 양 끝까지 채우기 위해 `width: 100vw; margin-left: calc(50% - 50vw);` 트릭을 상위 단일 래퍼로 일원화했다.
- **여백 충돌 제거**: 개별 컴포넌트가 자기 바깥쪽 `margin`을 갖는 관행을 금지하고, 부모 컨테이너가 `flex-direction: column`과 `gap`으로 섹션 간격을 일괄 제어하도록 통일했다.

```tsx
// 부모가 gap으로 자식 간격을 전담 — 자식은 외부 여백을 모른다
<Container style={{ display: 'flex', flexDirection: 'column', gap: isMobile ? '40px' : '64px' }}>
  <SolvookPassSection data={mainData.pass} />
  <SelectedBookSection data={mainData.selected} />
  <RankingSection data={mainData.ranking} />
</Container>
```

### 3. 단일 슬라이드 캐러셀의 깜빡임 트러블슈팅
메인 배너를 구현하던 중, 이벤트 배너가 1개만 등록되었을 때 무한 루프(`infinite: true`) 옵션 탓에 슬라이드가 비정상 복제되며 화면이 주기적으로 깜빡이는 현상이 발생했다.

이를 `infinite: items.length > 1`로 동적 제어하고, 미디어쿼리 CSS로 `display: none`을 토글하던 것을 디바이스 감지 훅(`useWindowDimensions`)을 통해 활성 디바이스에 맞는 1벌의 이미지만 DOM에 렌더하도록 최적화했다.

## 결과

- **공통 컴포넌트 통일**: 홈 화면 전용으로 쪼개질 뻔했던 카드를 홈, 검색 결과, 카테고리 뷰어, 마이페이지까지 100% 동일한 컴포넌트로 공통화했다.
- **프론트엔드 유지보수 비용 제로**: 신규 과목 런칭 및 프로모션 문구 변경 시 프론트엔드 배포 없이 실시간 운영 대응이 가능해졌다.
- **레이아웃 안정성 확보**: 스켈레톤 UI를 실제 카드 크기와 1:1로 맞추고 CLS(Cumulative Layout Shift) 및 배너 깜빡임을 완전히 제거했다.

## 회고

UI 컴포넌트를 설계할 때 가장 경계해야 하는 것은 **컴포넌트가 과도하게 똑똑해지는 것**이다.

컴포넌트 안에 `if`문이 많아질수록 그 컴포넌트는 재사용성을 잃고 특정 화면에 종속된다. 컴포넌트는 바보처럼 단순하게(Dumb Component) 만들고, 복잡한 비즈니스 표현의 책임은 데이터 계층으로 내려보내는 것이 장기적인 유지보수성을 지키는 가장 확실한 길임을 다시 한번 체감했다.
