"멋있어 보이는 아키텍처"가 팀을 괴롭힐 때가 있다.

수업 관리 웹 애플리케이션의 프론트엔드 코드베이스에 합류했을 때 마주한 구조가 그랬다. 백엔드에서 쓰던 DDD(도메인 주도 설계) 계층 구조가 프론트엔드에 그대로 복사되어 있었다. 폴더를 열면 `domain/model`, `domain/service`, `repositories`, `data-transfers`, `application/service`가 질서정연하게 자리 잡고 있었다. 얼핏 보면 대규모 엔터프라이즈의 견고한 아키텍처 같았다.

하지만 파일 안으로 들어가자마자 숨이 턱 막혔다.

## 문제

필드 하나를 화면에 띄우려면 5개 파일을 열어야 했다.

예를 들어 시험지(`ExamPaper`)에 `title` 필드 하나가 새로 생겼다고 하자. 이 단순한 값을 화면에 반영하기 위해 거쳐야 하는 경로는 이랬다:

1. `data-transfers/exam-paper.dto.ts`에 필드 추가
2. `repositories/exam-paper.repository.ts`에서 API 호출
3. `mappers/exam-paper.mapper.ts`에서 DTO를 도메인 모델로 1:1 복사
4. `domain/model/exam-paper.model.ts` 빈 클래스(Anemic Model)에 getter/setter 추가
5. `domain/service/exam-paper.service.ts`를 거쳐
6. `hooks/useExamPaper.ts`에서 호출
7. 마침내 `components/ExamPaperView.tsx`에서 렌더

```text
[API 응답 JSON]
   ↓
ExamPaperDTO (data-transfers)
   ↓ (1:1 필드 복사 매퍼)
ExamPaperModel (domain/model — 비즈니스 로직 없는 빈 클래스)
   ↓
ExamPaperRepository (repositories)
   ↓
ExamPaperService (domain/service)
   ↓
useExamPaper (hooks)
   ↓
[React Component]
```

비즈니스 로직이 풍부해서 도메인 모델이 스스로 불변식을 검증하고 있다면 모를까, 대부분의 도메인 모델은 서버에서 온 JSON을 그대로 담는 빈 껍데기(Anemic Model)였다. DTO와 도메인 모델 사이의 매퍼는 `title: dto.title`, `id: dto.id`처럼 이름만 옮겨 적는 기계적 타이핑의 연속이었다.

정작 프론트엔드에서 진짜 중요한 문제들 — **캐시 무효화 시점, 로딩과 에러 상태 제어, 화면 깜빡임 없는 낙관적 업데이트(Optimistic Update)** — 은 이 5겹 레이어 어디에도 자연스럽게 안착하지 못하고 레이어 사이사이에 파편화되어 있었다.

신규 입사자는 간단한 수정 하나에도 길을 잃었고, "이 코드는 repository에 둬야 하나요, service에 둬야 하나요?"라는 질문으로 리뷰 시간이 소모됐다.

## 트레이드오프 결정

백엔드의 정답이 프론트엔드의 정답은 아니다.

백엔드 DDD는 도메인의 무결성을 지키고 DB 영속성 계층과 비즈니스 규칙을 격리하는 데 탁월하다. 하지만 프론트엔드의 본질은 다르다. **프론트엔드는 서버 상태(Server State)의 원격 복제본을 가져와(fetch), 적절히 캐시하고(cache), 사용자에게 보여주며(render), 사용자 인터랙션을 서버로 전달하는 것**이다.

도메인 로직의 90%는 이미 서버 API 뒤에 숨어 있다. 프론트엔드가 자체적으로 무거운 도메인 모델을 복제해 유지하려 들면, 서버와의 동기화 비용과 보일러플레이트만 기하급수적으로 늘어난다.

그래서 팀에 제안했다. **과적용된 DDD 레이어를 걷어내고, SWR과 기능별 콜로케이션(Colocation)으로 단순화하자**고.

물론 레이어를 없애면 '관심사의 엄격한 분리'라는 교과서적 우아함은 잃는다. 하지만 우리가 얻는 건 압도적인 단순함과 개발 속도, 그리고 프론트엔드 생태계 표준 도구(SWR/React Query)가 제공하는 강력한 캐싱 인프라였다.

## 접근

5단계 파이프라인을 부수고, 관련 코드를 한곳으로 모았다(Colocation).

### 1. DTO 매퍼와 빈 도메인 클래스 제거
서버 응답 인터페이스와 화면 요구사항이 일치하면, 중간 매퍼 없이 TypeScript 타입으로 직접 사용했다. 화면 전용 가공이 필요한 경우에만 뷰 헬퍼 함수를 컴포넌트 근처에 두었다.

### 2. SWR 중심의 얇은 API 레이어로 통합
`Repository`와 `Service` 클래스를 모두 지우고, SWR 훅 하나로 캐싱·재요청·상태를 관리했다.

```ts
// AS-IS: 5개 파일로 쪼개져 있던 수십 줄의 보일러플레이트
// TO-BE: SWR 훅 하나로 fetch + 캐시 + 상태 관리 끝
export function useExamPaper(paperId: string) {
  return useSWR<ExamPaper>(
    paperId ? `/api/exam-papers/${paperId}` : null,
    fetcher,
    { revalidateOnFocus: false, dedupingInterval: 5000 }
  );
}
```

### 3. 기능(Feature) 기반 폴더 구조
레이어별로 가로로 쪼개져 있던 파일들을 기능(Feature) 단위로 세로로 모았다:

```text
features/exam-paper/
├── api/          # SWR 훅과 API fetcher
├── components/   # 시험지 전용 UI 컴포넌트
└── types/        # 타입 정의
```

시험지 기능을 고칠 땐 `features/exam-paper/` 폴더 하나만 열면 모든 맥락이 파악되도록 재배치했다.

## 결과

새 기능을 추가할 때 만들어야 하는 파일이 **5~6개에서 1~2개**로 줄었다.

- **온보딩 비용 감소**: "어느 레이어에 코드를 넣어야 하는지" 고민할 필요 없이, `api/`에 훅을 두고 `components/`에서 부르면 끝나는 명확한 멘탈 모델이 정착됐다.
- **캐시 일관성 확보**: 기존에 Repository에 억지로 구현하려다 버그를 내던 인메모리 캐시 대신, SWR의 키 기반 캐시 무효화(`mutate`)를 사용해 상태 불일치 버그가 사라졌다.
- **코드량 대폭 감소**: 의미 없는 1:1 매핑 코드와 getter/setter 수백 줄이 코드베이스에서 삭제됐다.

## 회고

이 프로젝트를 겪으며 아키텍처를 바라보는 시각이 크게 바뀌었다.

교과서에 나오는 유명한 아키텍처 패턴이라도, **현재 도메인의 본질과 맞지 않으면 그저 비용이고 부채**다. 백엔드에서 훌륭한 패턴이 프론트엔드에서는 족쇄가 될 수 있고, 그 반대도 마찬가지다.

진짜 좋은 아키텍처는 레이어가 얼마나 정교한가가 아니라, **팀원들이 비즈니스 문제를 해결할 때 겪는 불필요한 마찰을 얼마나 덜어주는가**로 증명된다. 멋있는 구조를 걷어내고 단순한 본질로 돌아갈 수 있는 용기가 필요하다는 것을 배웠다.
