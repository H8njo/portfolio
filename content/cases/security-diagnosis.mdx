폐쇄망 환경의 공공/기업 보안 진단 시스템을 맡았을 때 가장 먼저 체감한 것은, **이곳의 모든 업무 데이터는 엑셀(Excel)로 시작해 엑셀로 끝난다**는 점이었다.

진단 항목 설정, 점검 결과 제출, 통계 산출까지 담당자들은 화면에서 하나씩 입력하기보다 엑셀 파일로 내려받아 오프라인에서 작업한 뒤 다시 업로드하는 워크플로우를 절대적으로 선호했다. 엑셀 입출력은 단순한 부가 기능이 아니라 시스템의 핵심 생명선이었다.

초기 커리어 시절, "엑셀 연동쯤이야 라이브러리로 데이터 읽어서 보내면 끝나는 것 아닌가"라고 쉽게 생각했다가 혹독한 현실을 마주했다. 엑셀은 **사람의 눈에 보이는 값과 내부 메모리에 저장된 진짜 값이 완전히 다른 거대한 복잡성의 덩어리**였기 때문이다.

## 1. 문제: 엑셀 파이프라인에서 터진 3가지 복합 장애

다운로드는 그럭저럭 해결했다. 테이블의 `columns` 메타데이터를 파싱하여 화면에 표시되는 텍스트(예: "조치완료")와 DB 코드 ID를 역매핑하는 동적 변환기를 만들어 화면과 엑셀의 정합성을 맞췄다.

진짜 위기는 수천 건의 점검 결과가 업로드되는 입력 파이프라인에서 터졌다:

1. **대량 POST 요청으로 인한 서버 다운**: 담당자가 한 번에 수천 건의 진단 결과 행을 담은 엑셀을 업로드하면, 수 메가바이트의 거대한 단일 페이로드가 서버로 전송되어 백엔드 프로세스가 메모리 고갈과 타임아웃으로 뻗어버렸다.
2. **업로드할 때마다 데이터가 기하급수적으로 복제되는 현상**: 진단 결과 회신 화면에서 같은 엑셀 파일을 수정해 다시 올리면, 기존 데이터가 갱신되는 것이 아니라 매번 새로운 행으로 계속 추가(Insert)되어 데이터베이스가 오염되었다.
3. **날짜가 시리얼 정수로 박히는 데이터 왜곡**: 화면에서는 분명 `2020-12-14`로 보이던 점검일자가, DB에는 `44179`라는 정체불명의 정수로 영속화되어 통계 쿼리가 마비되었다.

## 2. 해결책: 데이터 파이프라인과 정합성 정상화

### ① 50건 청크 분할 전송과 실시간 진행률 UX

서버 타임아웃 시간을 단순히 늘리는 것은 근본적인 해결책이 아니었다. 클라이언트 레벨에서 **배열을 50건 단위의 청크(Chunk)로 쪼개어 순차적으로 전송하는 파이프라인**을 구축했다:

```js
const limit = 50;
const total = dataWillCreateToDB.length;
const result = [];

for (let current = 0; current <= total; current += limit) {
  // 실시간 업로드 진행률 계산
  setUploadProgress({ percent: Math.round((current / total) * 100) });
  
  const chunk = dataWillCreateToDB.slice(current, current + limit);
  result.push(await diagApi.post('/diag-results/reply', chunk));
}

setUploadProgress({ percent: 100 });
```

한 번에 서버에 실리는 요청 부하를 50건으로 고정하여 서버 다운을 원천 차단했다.

또한 수천 건이 처리되는 동안 화면이 멈춘 것처럼 보이면 사용자가 불안해하며 새로고침을 누르는 문제를 막기 위해, 청크 루프마다 `setUploadProgress`로 진행률 게이지를 부드럽게 렌더링했다. 성능 안정성을 위해 설계한 배치가 훌륭한 사용자 경험(UX)으로 이어진 셈이다.

### ② 신규 생성(Create)과 회신(Upsert) 엔드포인트의 명확한 분리

데이터가 무한 복제되던 원인은 단순하지만 치명적인 엔드포인트 착오였다. 회신 업로드임에도 신규 생성 전용 엔드포인트(`/upload`)로 요청을 보내고 있어, 서버가 무조건 `INSERT` 쿼리를 실행했던 것이다.

```diff
- result.push(await diagApi.post('/diag-results/upload', chunk));
+ result.push(await diagApi.post('/diag-results/reply', chunk));
```

수정된 코드는 단 한 줄이었지만 얻은 교훈은 막대했다. **화면상으로는 똑같은 '엑셀 업로드' 버튼이라도, 서버 입장에서는 '신규 생성'과 '기존 레코드 갱신'이라는 완전히 다른 연산**이다. 이후 컴포넌트 레벨에서 Create와 Reply 워크플로우의 분기를 물리적으로 명확히 분리했다.

### ③ 엑셀 시리얼 날짜(`44179`)의 정밀 역산 변환

`44179`라는 숫자는 엑셀이 날짜를 1900년 1월 1일을 기준으로 한 '경과 일수(시리얼 정수)'로 저장하기 때문에 발생한 현상이었다. 화면에서는 엑셀 프로그램이 날짜 포맷을 씌워 보여주었을 뿐, 원본 셀에 저장된 실제 데이터는 정수였던 것이다.

이를 자바스크립트 표준 `Date` 객체로 안전하게 변환하는 보정 알고리즘을 구축했다:

```js
const formatExcelDate = (excelSerialDate) => {
  // 25569: 엑셀 Epoch(1900-01-01)와 유닉스 Epoch(1970-01-01) 사이의 일수 차이 (윤년 오차 포함)
  const date = new Date((excelSerialDate - 25569) * 86400 * 1000);
  const year = date.getFullYear();
  const month = String(date.getMonth() + 1).padStart(2, '0');
  const day = String(date.getDate()).padStart(2, '0');
  return `${year}-${month}-${day}`;
};

if (data.startDate || data.endDate) {
  data.startDate = formatExcelDate(data.startDate);
  data.endDate = formatExcelDate(data.endDate);
}
```

`25569` 상수를 활용해 엑셀의 Epoch 기준점을 유닉스 타임스탬프 밀리초로 정확히 환산하여, DB에 정상적인 `YYYY-MM-DD` 문자열로 안착되도록 해결했다.

## 결과

* **대용량 업로드 안정성 100% 확보**: 단일 요청 부하를 50건 청크로 고정하여, 수만 건의 진단 결과 데이터가 유입되어도 서버 타임아웃이나 프로세스 다운 없이 안정적으로 수용하게 되었다.
* **데이터 정합성 보장**: 회신 엔드포인트 분리로 중복 레코드 누적을 완전히 차단하고, 엑셀 시리얼 날짜 보정을 통해 통계 및 보고서 쿼리의 정확도를 완벽히 회복했다.
* **전사 테이블 엑셀 다운로드 표준화**: 메타데이터 기반의 동적 코드 변환 규약을 시스템 전 페이지(진단, 침해, 통계, 네트워크)로 확장하여 전사 공통 모듈로 정착시켰다.

## 회고: 화면에 보이는 값과 데이터의 실체는 다르다

이 프로젝트에서 마주한 모든 난관은 결국 하나의 진실을 가리키고 있었다:
**"사용자의 눈에 보이는 값과 시스템 내부에서 다루어지는 데이터의 실체는 완전히 다를 수 있다."**

화면의 "조치완료"는 DB에서는 코드 ID였고, 화면의 `2020-12-14`는 엑셀 내부에서는 `44179`라는 정수였으며, 똑같이 생긴 '업로드' 버튼은 서버 관점에서는 완전히 다른 트랜잭션이었다.

초기 커리어에 엑셀과 대용량 데이터가 지닌 수많은 엣지 케이스를 밑바닥부터 정면으로 마주하고 풀어본 경험은, 지금까지도 복잡한 엔터프라이즈 시스템을 설계할 때 데이터의 실제 형태와 트랜잭션의 책임을 가장 먼저 의심하고 철저히 검증하는 단단한 엔지니어링 기본기가 되어주고 있다.
