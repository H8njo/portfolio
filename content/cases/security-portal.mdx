대규모 공공 통합 관리 시스템 구축 프로젝트에 합류했을 때, 기획 시안을 받아보고 입이 떡 벌어졌다. 만들어야 할 화면 페이지만 100장이 훌쩍 넘어가고 있었다.

회원 관리, 정책 설정, 감사 로그, 통계 지표, 시스템 설정 등 다뤄야 할 도메인이 100개가 넘는 거대한 포털이었다. 하지만 프론트엔드 개발자는 나를 포함해 **단 두 명**뿐이었다.

주먹구구식으로 화면을 하나씩 찍어내선 마감 기한을 절대 맞출 수 없었다. 가장 효율적으로 프로젝트를 완수하기 위해, 코드를 작성하기 전에 **재사용할 수 있는 패턴과 UI 구조부터 샅샅이 분석**하기 시작했다.

각 페이지들의 깊이(Depth)와 계층 구조를 정의하고, 공통적으로 사용되는 UI 패턴끼리 묶어냈다. 화면마다 다루는 데이터와 세부 기능은 묘하게 달랐지만, 유저 경험(UX) 기반의 디자인 시스템이 일관되게 적용되어 있었기에 시각적인 골격과 인터랙션 패턴은 거의 동일했다:
- 목록을 보여주고 (Table)
- 조건을 걸어 검색하고 (Search Filter)
- 컬럼별로 정렬하고 (Sort)
- 데이터를 엑셀로 내려받거나 일괄 업로드하고 (Excel I/O)
- 추가/수정/삭제 모달 폼을 띄우며 (CRUD Modal)
- 사용자의 역할과 조직에 따라 권한을 제어하는 것 (RBAC)

컴포넌트 구조를 설계하기 전에 선행한 이 철저한 UI 구조 분석을 통해, 100장이 넘는 화면의 차이점을 딱 하나로 압축할 수 있었다 — **어떤 컬럼을 보여주고 조작하느냐.**

나머지 모든 UI와 인터랙션은 **단 하나의 조립식 테이블 컴포넌트**가 메타데이터를 받아 전자동으로 처리하도록 아키텍처를 세웠다. 실제로 `pages/` 아래 59개 파일이 단 한 줄의 중복 코드 없이 이 컴포넌트 하나만을 임포트해 완성되었다.

## 개발 방식: 가장 복잡한 기준 페이지에서 출발해 점진적 확장으로

처음부터 100개 도메인의 모든 케이스를 머릿속으로만 상상하며 거대한 시스템을 한 번에 만들려 하지 않았다. 대신 **가장 까다롭고 모든 기능과 예외 케이스가 총망라된 가장 복잡한 페이지부터 제작**하기 시작했다.

단순한 페이지를 기준으로 컴포넌트를 만들면 나중에 복잡한 화면을 만났을 때 구조를 다 뜯어고쳐야 하지만, 가장 복잡한 페이지를 기준으로 삼아 뼈대를 단단하게 잡아두면 나머지 화면들은 필요한 옵션만 켜고 끄며 쉽게 대응할 수 있기 때문이었다.

첫 페이지를 만들 때 모든 컴포넌트가 확장과 재사용에 유연하게 대응할 수 있도록 아키텍처를 세밀하게 다듬다 보니, 초기 개발 시간이 다소 걸렸다. 함께 개발하던 동료 파트너는 "만들어야 할 화면이 100장이 넘어가는데 첫 페이지부터 이렇게 오래 걸리면 기한을 맞출 수 있을까?"라며 불안해하기도 했다. 하지만 내 머릿속에는 이미 메타데이터 기반의 전체 확장 설계가 완벽하게 그려져 있었다.

> "걱정하지 마세요. 지금 이 기준 컴포넌트 하나만 단단하게 완성해 두면, 다음 페이지부터는 찍어내듯 순식간에 끝낼 수 있습니다."

동료를 안심시키며 첫 기준 페이지를 묵직하게 완성해 냈다. 그리고 내 예상은 정확히 들어맞았다.

가장 복잡한 기준 페이지가 완성된 후 다음 페이지들을 하나씩 붙여나가면서:
- "이 화면은 추가/수정/삭제 버튼이 없어야 해" → `useAdd`, `useEdit`, `useRemove` prop으로 제어
- "이 화면은 엑셀 업로드 템플릿이 달라" → `excelImport`, `excelExport` prop으로 오버라이드
- "이 화면은 잠긴 행(Row)은 수정하면 안 돼" → `allowEdit(record)` 훅 함수를 prop으로 주입

페이지가 늘어날 때마다 조금씩 달라지는 세부 요구사항들을 `props`와 확장 슬롯으로 유연하게 넘겨받을 수 있도록 컴포넌트를 점진적으로 진화시켰다.

이 방식 덕분에 모든 케이스를 수용할 수 있는 튼튼한 컴포넌트 하나로, 이후 50여 개가 넘는 신규 화면들은 **단순히 컬럼 배열과 쿼리만 prop으로 넘기며 번개 같은 속도로 찍어낼 수 있었고, 개발 시간을 극단적으로 단축**할 수 있었다.

## 화면마다 필요한 게 다 달랐다

문제는 "똑같은 표"가 사실 하나도 안 똑같았다는 거다. 화면을 모아 놓고 보니 필요한 기능이 이만큼이었다:

- **목록 표시** — 타입별 셀 렌더(날짜/숫자/코드값 뱃지), 말줄임+툴팁, 행 번호
- **검색** — 화면에 따라 텍스트 한 칸부터 기간 + select 다섯 개까지. 접었다 펴기, 조건 딥링크
- **정렬** — 컬럼별 오름/내림차순, 정렬 제외 컬럼
- **엑셀** — 내보내기(코드값→한글 라벨 변환), 가져오기(행 단위 등록)
- **CRUD 모달** — 컬럼 정의로 자동 생성되는 추가/수정 폼, 다열 레이아웃
- **행 선택 / 일괄 작업** — 페이지 넘어가는 선택 유지, 일괄 삭제 + 커스텀 일괄 액션
- **컬럼 조작** — 표시/숨김 토글, 순서 드래그 변경, 너비 리사이즈, 그 설정의 화면별 저장
- **인라인 편집** — 목록 위에서 셀 값만 바로 수정·저장
- **권한** — 사용자 역할마다 다른 조회/수정 범위에 따라 버튼 노출 제어

한 컴포넌트가 이걸 다 하되, 화면마다 **필요한 것만 골라 켜지게** 해야 했다. 안 그러면 "이 화면만 좀 달라요"가 나올 때마다 컴포넌트 밖에 특수 코드가 쌓이고, 결국 복사 붙여넣기 지옥으로 돌아간다.

## 설계 축: 하나의 정의, 다섯 개의 얼굴

핵심 통찰은 이거였다.

> 컬럼 하나가 다섯 군데에서 서로 다르게 해석돼야 한다.

같은 `status` 컬럼이 **표**에선 색깔 뱃지로, **검색**에선 select로, **엑셀**에선 코드값을 한글 라벨로 풀어서, **폼**에선 입력칸으로 보이고, 어떤 화면에선 아예 **폼에서만 숨는다.** 그래서 컬럼 객체 하나에 플래그를 달아 다섯 갈래로 흘려보냈다. 정의는 한 벌, 해석은 다섯 갈래.

```jsx
// 컬럼 한 벌이 표·검색·엑셀·폼을 전부 만든다
{
  dataIndex: 'status',
  title: '상태',
  render: (v) => <StatusBadge value={v} />,   // 표: 뱃지
  searchDefine: { type: 'select', options },  // 검색: select
  excelValueEnum: STATUS_LABELS,              // 엑셀: 코드→한글
  editable: false,                            // 폼: 수정 시 잠금
  hideSorting: true,                          // 정렬: 제외
}
```

추가·수정 모달도 표에 쓴 그 배열을 그대로 폼으로 넘긴다. 같은 정의니까 표와 폼이 어긋날 일이 없다. 수정할 땐 바뀐 필드만 — 초기값과 다른 키만 추려 보냈다. 안 그러면 안 건드린 필드까지 통째로 덮어쓰니까.

```jsx
// 수정은 diff만
if (isUpdate) {
  R.keys(value).forEach((key) => {
    if (value[key] !== initialValues[key]) valueForUpdate[key] = value[key];
  });
}
```

신규 화면은 여기까지 오면 "컬럼 배열 작성 + 쿼리 연결"로 끝난다.

## 화면 하나는 이만큼이면 끝난다

정책 관리 화면 하나를 통째로 옮기면 이렇다. 컬럼 배열이 표·검색·엑셀·폼을 다 만들고, `<Table>`은 데이터와 CRUD 함수만 받는다.

```jsx
// pages/policy/setting.jsx — 이 파일이 화면의 전부다

const columns = [
  { dataIndex: 'title', title: '정책명',
    searchDefine: { type: 'text' } },              // 표 + 검색(텍스트)

  { dataIndex: 'status', title: '상태',
    render: (v) => <StatusBadge value={v} />,      // 표: 색깔 뱃지
    searchDefine: { type: 'select', options },     // 검색: select
    excelValueEnum: STATUS_LABELS },               // 엑셀: 코드→한글

  { dataIndex: 'description', title: '상세 설명' }, // 표 + 폼(기본 입력칸)

  { dataIndex: 'updatedAt', title: '최종수정일',
    valueType: 'dateTime',                         // 표: 날짜 포맷
    searchDefine: { type: 'dateRange' },           // 검색: 기간 선택
    editable: false },                             // 폼: 수정 시 잠금
];

export default function PolicySettingPage() {
  const { data, loading, refetch } = usePolicyList(); // 쿼리만 연결

  return (
    <Table
      tableItemName="정책"
      columns={columns}
      dataSource={data}
      loading={loading}
      refetch={refetch}
      onAdd={(v) => createPolicy(v)}               // CRUD 주입
      onEdit={(id, v) => updatePolicy(id, v)}
      onDelete={(id) => deletePolicy(id)}
    />
  );
}
```

이게 화면 파일 전부다. 검색 폼, 정렬, 추가·수정·삭제 모달, 페이지네이션, 행 선택은 한 줄도 안 짰지만 다 나온다 — 컬럼 배열에 이미 다 적혀 있으니까. 추가·수정·삭제 버튼은 경로(`/policy/setting`)에서 권한을 물어 스스로 나타나고 사라진다.

엑셀도 마찬가지다. **다운로드**는 컬럼과 `dataSource`가 있으니 자동으로 뜬다 — 컬럼의 `title`을 헤더로, `excelValueEnum`으로 코드값을 한글로 풀어서 `정책_목록.xlsx`를 내린다. **업로드**는 이미 연결한 `onAdd`에 그대로 물린다. 사용자가 올린 시트의 각 행이 `onAdd`로 흘러 들어가 그대로 등록된다. 화면은 파싱도 매핑도 신경 쓸 게 없다.

```jsx
// 엑셀 커스터마이징이 필요할 때만 한 줄 (기본은 자동)
<Table
  columns={columns}
  dataSource={data}
  onAdd={(v) => createPolicy(v)}                       // 업로드가 이 함수로 흘러든다
  excelExport={{ fileName: '정책설정_현황' }}             // 다운로드 파일명 override
  excelImport={{ template: POLICY_TEMPLATE }}          // 업로드 양식 지정
/>
```

화면 59개가 이 모양으로 생겼다.

## 조립식으로 확장한다

"필요한 것만 골라 켠다"를 세 층의 조립 지점으로 나눴다. 화면은 이 셋을 조합해 자기 모양을 만든다.

**1. 컬럼 플래그 — 선언으로 켜고 끈다.** 컬럼 객체에 플래그만 얹으면 동작이 바뀐다. `searchDefine`이면 검색 입력으로, `export: false`면 엑셀에서 제외, `excelValueEnum`이면 엑셀에서만 다른 라벨, `editable: false`면 폼에서 잠금, `table: false`면 표에선 숨기고 폼에만, `hideSorting`이면 정렬 후보에서 제외. 화면 하나가 표 30컬럼짜리든 검색 한 칸짜리든, 코드가 아니라 데이터로 표현된다.

**2. 슬롯 — 자리를 열어두고 끼워 넣는다.** 툴바에 이 화면만의 버튼이 필요하면 `customToolbar`로 끼우고, 행 오른쪽에 "상세보기·재발송" 같은 액션이 필요하면 액션 컬럼 렌더러로 넣는다. 검색 폼·툴바·헤더·선택 알림줄이 전부 열린 슬롯이라, 컴포넌트를 건드리지 않고 화면에서 채운다.

**3. 훅 — 흐름을 가로챈다.** 기본 동작으로 안 되는 화면을 위해 가로채기 지점을 뒀다. `beforeAdd`·`beforeEdit`로 모달을 열기 전에 끼어들고, `checkValidation`으로 제출을 막고, `allowEdit(record)`로 특정 행만 수정 불가로 만들고, `handleMultipleRows.addon`으로 일괄 작업 메뉴에 임의 액션을 더한다. CRUD 자체는 `onAdd`·`onEdit`·`onDelete`로 주입하니 GraphQL이든 REST든 상관없다.

앞의 화면에 특화된 요구사항이 붙어도, 확장은 한 줄씩이다.

```jsx
<Table
  columns={columns}
  dataSource={data}
  // ...
  {...useColumnsState()}                               // 프리셋: 컬럼 설정 저장
  allowEdit={(row) => row.locked}                       // 훅: 잠긴 행은 수정 불가
  customToolbar={() => <SyncExternalData />}           // 슬롯: 이 화면만의 버튼
  handleMultipleRows={{ addon: [bulkApproveAction] }}   // 훅: 일괄 "승인" 액션 추가
/>
```

자주 쓰는 조합은 프리셋으로 굳혔다. 읽기 전용 목록은 `CommonTable`이 추가·수정·삭제를 다 꺼둔 채 데이터만 물어오고, `useColumnsState`를 끼우면 표시/숨김·순서·너비 설정이 **화면 경로별로 localStorage에 남아** 새로고침해도 유지된다.

## 그래서 모든 케이스가 흡수됐다

이 조립 구조 덕에, "이 화면만 달라요"가 컴포넌트 밖으로 새지 않았다.

- 컬럼 30개짜리 대규모 데이터 화면 → 컬럼 표시 토글 + 순서 드래그 + 너비 리사이즈로 사용자가 직접 화면을 맞추고, 그 설정은 경로별로 저장된다.
- 검색이 복잡한 화면 → 텍스트·숫자·기간·select를 컬럼이 직접 고르고, 조건을 URL 쿼리에 실어 "특정 조건 3페이지"를 그대로 링크로 공유한다.
- 모달이 과한 화면 → 인라인 편집 셀로 목록 위에서 값 하나만 바꿔 저장한다.
- 권한이 화면마다 다른 상황 → 아래 방식으로 버튼이 스스로 나타나고 사라진다.

새 요구가 오면 컴포넌트에 플래그·슬롯·훅 중 맞는 확장점을 하나 더 열었다. 화면 쪽 코드는 늘 컬럼 배열 수준으로 얇게 유지됐다.

## 예기치 못한 위기: 수많은 관리자 권한 분기, 그리고 뜻밖의 해결

개발이 한창 진행되던 중, 예상치 못한 큰 난관을 마주했다. 바로 **다단계 관리자 권한**(RBAC) 설정이었다.

조직마다, 직급마다 "어떤 관리자는 조회만, 어떤 관리자는 추가/수정까지, 어떤 관리자는 엑셀 다운로드만" 권한이 세밀하게 쪼개져 있었다. 100여 개 화면마다 수많은 관리자 역할에 맞춰 버튼 노출과 기능 접근을 일일이 제어해야 하는 상황을 마주했을 때, 순간 '아, 50개가 넘는 화면에 권한 분기 코드를 일일이 다 쳐넣어야 하나? 어떡하지?'라는 아찔한 위기감이 스쳤다.

하지만 위기의 순간, **모든 화면이 단 하나의 공통 컴포넌트를 공유하고 있다는 사실이 결정적인 구원투수**가 되어주었다.

화면마다 손을 댈 필요가 전혀 없었다. **라우트 경로를 권한의 원천**으로 삼는 간단한 권한 판정 유틸 하나를 공통 `Table` 컴포넌트 내부에 심어주기만 했다.

라우트 정의 한 벌에서 메뉴 트리도, 권한 설정 트리도, 런타임 체크 키도 나온다. 권한 키는 그냥 `경로/액션`(`user.hasPermission('${pathname}/CREATE')`)이다. `Table` 컴포넌트는 현재 접속한 URL 경로를 스스로 물어보고, 권한이 있을 때만 추가/수정/삭제 및 엑셀 버튼을 렌더링한다.

```jsx
// Table 컴포넌트 내부: 현재 경로 기준으로 권한을 물어 스스로 버튼을 제어한다
const permissionCreate = user.hasPermission(`${path || pathname}/CREATE`);
const permissionUpdate = user.hasPermission(`${path || pathname}/UPDATE`);
const permissionDelete = user.hasPermission(`${path || pathname}/DELETE`);
```

개별 화면 파일들은 단 한 줄의 권한 분기 코드도 작성하지 않았지만, 59개 전체 화면의 모든 버튼이 관리자의 역할에 따라 스스로 나타나고 사라지는 복잡한 권한 제어가 **단 몇 줄의 공통 유틸 주입으로 완벽하고 신속하게 해결**되었다. 컴포넌트 재사용 설계의 진정한 위력이 빛을 발한 순간이었다.

## 계약은 사람이 아니라 구조가 지키게

추상화 한 곳에 몰아넣은 만큼, 계약도 한 곳에서 지켜야 했다.

페이지네이션이 대표적이었다. 검색·정렬·필터를 바꿀 때 페이지를 1로 안 돌려놓으면, 3페이지를 보다 검색했을 때 직전 offset이 살아남아 엉뚱한 `start`로 쿼리가 나가 결과가 비어 보인다. 핸들러마다 "여기도 리셋"을 사람이 챙기면 반드시 빠뜨린다. 그래서 **입력이 바뀌는 모든 경로가 무조건 1페이지를 통과하도록** 한 곳에 강제했다. 페이지 넘어가는 다중 선택도 마찬가지 — "현재 페이지 이벤트"와 "전역 선택 상태"를 분리해 훅 한 곳에서 병합·차감하게 묶었다. 빠뜨리기 쉬운 계약일수록 컴포넌트가 대신 지킨다.

## 결과

화면 59개, 도메인 100여 개를 두 명이 굴렸다. 새 CRUD 화면 하나가 "컬럼 배열 작성 + 쿼리 연결"로 끝나니, 화면을 찍어내는 속도가 확 빨라졌다. 한 번 잡은 버그는 59개 화면에서 한꺼번에 고쳐졌다.

그리고 이 테이블은 이 포털 안에서 끝나지 않았다. 검색·정렬·엑셀·모달폼이 붙는 리스트/디테일 화면은 어디든 컬럼만 다를 뿐 골격이 똑같으니까, 이후 다른 프로젝트들에서도 컬럼 배열만 갈아끼워 그대로 가져다 썼다. 확장점을 플래그·슬롯·훅으로 열어둔 덕에, 새 프로젝트의 낯선 요구도 컴포넌트를 다시 만들지 않고 확장점 하나를 더 여는 걸로 흡수됐다.

정의를 한곳에 모으면 값이 한곳에서 나온다. 화면의 정의는 컬럼 배열로, 권한의 정의는 라우트로, 흐름의 계약은 훅으로 모았다. 흩어질 진실을 한곳에 묶고, 다양성은 조립 지점으로 열어두는 것 — 재사용성과 확장성은 그 둘을 동시에 잡을 때 나왔다.

## 회고 — 확장의 유연함과 오버엔지니어링의 경계

이 프로젝트는 내게 **앞으로 어떤 비즈니스 요구사항이 튀어나올지 모르기 때문에, 핵심 컴포넌트는 언제나 확장에 열려 있는 유연한 구조로 설계해야 한다**는 값진 교훈을 남겼다. 플래그, 슬롯, 훅이라는 확장 지점을 열어두지 않았다면 59개 화면의 서로 다른 예외들을 결코 흡수하지 못했을 것이다.

하지만 동시에 **너무 많은 미래를 미리 고려하고 지나치게 넓혀두면 오버엔지니어링의 덫에 빠진다**(Over-engineering)는 뼈아픈 반면교사도 얻었다.

솔직히 말하면, 이 `Table`은 거대한 God component였다. 렌더링, 검색, 정렬, 페이지네이션, 엑셀 입출력, CRUD 모달, 권한 판정, 행 선택, 컬럼 상태 저장을 한 컴포넌트가 다 들고 있었다. prop이 40개를 넘었고, "테이블"이라는 이름 하나로 부를 수 없는 일을 혼자 다 떠안았다. 

두 명이 100개 도메인을 쳐내야 하는 절박한 상황에선 가장 빠른 답이었지만, 미래의 모든 가능성을 한 컴포넌트에 몰아넣으려다 보니 두 가지 문제가 터져 나왔다:
1. **prop 폭발**: 화면이 기능을 유연하게 "조립"하는 것이 아니라, 안 쓰는 기능까지 수십 개나 주렁주렁 매달고 있는 거대한 단일 인터페이스를 강제로 상속받는 꼴이 됐다.
2. **컬럼 플래그의 런타임 누수**: 컬럼 하나가 표·검색·엑셀·폼에서 다르게 해석되는데, 그 분기가 컴포넌트 내부에 숨어 있어 "표에선 멀쩡한데 엑셀에서만 깨지는" 오류를 타입 시스템이 잡지 못하고 런타임에 가서야 발견했다.

"혹시 이런 것도 필요하지 않을까?"라며 한곳에 모든 책임을 넓혀두는 것은 진정한 확장이 아니라 또 다른 기술 부채가 된다.

### 다시 만든다면: 오케스트레이션과 관심사의 분리

다음 프로젝트에서 이 구조를 발전시킨다면, 책임을 적절히 쪼개는 **헤드리스**(Headless)와 **컴파운드**(Compound) 아키텍처로 갈 것이다:

1. **헤드리스 코어로 상태와 계약 격리**: 쿼리 파라미터, 페이지네이션, 선택 상태 같은 비즈니스 로직을 `useTable()` 훅으로 내린다. 상태 계약은 훅이 엄격하게 지키고, 렌더링 책임은 완전히 밖으로 덜어낸다.
2. **컴파운드 컴포넌트로 관심사 조립**: 검색, 엑셀, 툴바, 페이지네이션을 prop이 아닌 `<TableView.Search>`, `<TableView.Excel>` 같은 자식 컴포넌트로 만든다. 필요한 화면에만 붙이고 안 쓰면 아예 트리에 올리지 않는 진짜 조립식이 된다.
3. **CRUD 모달과 권한의 경계 분리**: 폼 생성과 권한 판정은 "표를 그리는 일"이 아니다. 폼은 별도 `<RecordForm>`으로, 권한은 상위 라우트 가드나 `<Can>` 래퍼에서 결정해 테이블은 순수하게 렌더링에만 집중하도록 만든다.

```jsx
// 다시 만든다면: 상태는 훅으로, 관심사는 필요한 조각만 조립
const table = useTable({ columns, query });

<TableView {...table}>
  <TableView.Search />       {/* 검색이 필요한 화면만 */}
  <TableView.Excel />        {/* 엑셀이 필요한 화면만 */}
  <TableView.Pagination />
</TableView>
```

요지는 이렇다. **확장에 유연하되, 현재의 요구사항에 명확히 집중하는 것.** 미래의 가상 시나리오에 갇혀 오버엔지니어링에 빠지지 않고, 책임과 관심사를 적절히 쪼개는 아키텍처의 균형 감각이 진정한 시니어의 역량임을 배웠다.
