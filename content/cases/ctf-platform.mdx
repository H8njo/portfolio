누가 문제를 하나 맞히면, 그 문제를 **먼저** 푼 사람들 점수가 전부 실시간으로 조금씩 깎인다. 버그가 아니다. 그래야 정상이다.

CTF(해킹 방어 경진대회) 플랫폼의 실시간 자동 채점 및 스코어보드 시스템을 개발했다. 참가자가 직접 문제를 출제하고 다른 참가자가 이를 풀어내면, 격리된 샌드박스 워커가 정답(Flag)을 검증하고 즉시 점수를 매겨 스코어보드에 반영한다.

일반적인 퀴즈 플랫폼이라면 단순하다. 정답을 맞히면 고정된 100점을 더하고 끝내면 된다. 하지만 이 플랫폼의 채점 규칙은 완전히 달랐다. **아무도 못 푼 어려운 문제일수록 배점이 치솟고, 정답자가 많이 나올수록 문제 배점이 실시간으로 낮아지는 동적 스코어링**(Dynamic Scoring) 구조였다.

```js
// 정답자가 늘어날수록 분모가 커져 문제 배점이 실시간으로 떨어진다
const solveScore = totalUserCount / solveCount;
```

나눗셈 단 한 줄. 처음엔 이 간단한 수식이 귀여워 보였다. 하지만 이 한 줄이 프로젝트 전체에서 데이터 정합성을 두고 가장 깊게 고민하고 여러 번 수술하게 된 거대한 뇌관이 되었다.

## 문제: 나중 사건이 과거의 값을 소급해서 바꾼다

분모인 `solveCount`(정답자 수)는 누군가 정답을 맞힐 때마다 1씩 증가한다. 그 말은 — **누군가 지금 막 정답을 제출한 순간, 그 문제를 과거에 이미 풀어 점수를 획득했던 모든 선행 정답자의 점수도 동시에 깎여야 한다**는 뜻이다.

점수는 '내가 맞힌 순간에 확정되는 고정 불변의 값'이 아니었다. **뒤에 일어난 미래의 사건이 앞선 과거의 획득 점수를 소급해서 끌어내리는 역학**이었다. 분자인 `totalUserCount`(전체 참가자 수)도 마찬가지다. 신규 유저가 가입하거나 탈퇴하면, 그 순간 플랫폼의 모든 문제 배점이 한꺼번에 요동쳤다.

처음에는 가장 단순하고 직관적인 길을 택했다. 유저 테이블에 `totalScore`(총점) 컬럼 하나를 두고, 점수가 생길 때마다 그 칸에 숫자를 더해주는 방식이었다.

하지만 곧바로 치명적인 함정에 부딪혔다. 총점 한 칸에 모든 점수를 합산해버리면, **특정 문제의 배점이 변경되었을 때 과거에 그 문제를 푼 유저들의 총점에서 정확히 얼마를 차감해야 하는지 역추적할 방법이 전혀 없었다.** 이미 하나로 뭉쳐진 합계 컬럼은 과거의 개별 획득 이력을 기억하지 못하기 때문이다.

## 아키텍처 결정: 합계 컬럼 vs 이벤트 원장(Event Ledger)

데이터를 **합계 한 칸**으로 관리할 것인가, 아니면 **사건 한 건당 하나의 행**(Row)으로 기록할 것인가. 모든 설계의 갈림길이 여기서 시작되었다.

| 비교 항목 | 합계 컬럼 방식 (`totalScore`) | 이벤트 원장 방식 (`Scoreboard Ledger`) |
|:---|:---|:---|
| **저장 방식** | 유저당 단 1개의 총점 컬럼에 누적 합산 | 점수 변동 사건마다 1개 행씩 불변 기록 (Append-only) |
| **과거 소급** | ❌ 불가능 (개별 점수 분해 불가) | ✅ 완벽 지원 (특정 문제/유저별 소급 갱신 가능) |
| **랭킹 읽기** | 빠름 (`ORDER BY totalScore DESC`) | 합산 연산 필요 (`SUM(score) GROUP BY user`) |
| **정합성 검증** | 버그 발생 시 원인 추적 불가 | 모든 점수 획득 이력에 대한 감사 추적(Audit) 가능 |

동적 점수의 본질은 '과거 사건에 대한 실시간 소급 갱신'에 있었기에, 합계 컬럼 방식은 애초에 성립할 수 없었다. 점수 획득 사건이 일어날 때마다 원장에 행을 쌓는 **이벤트 원장**(Event Ledger) 모델로 전면 전환했다: `(userId, problemId, scoreType, problemType, score)`.

원장 방식을 택하자 **특정 문제의 정답 점수를 가진 모든 유저의 행**을 단 한 번의 키 질의로 정확히 짚어낼 수 있게 되었다.

나아가 테이블이 무한정 늘어나는 부담을 줄이기 위해, 출제 점수와 정답 점수, 개인전과 팀전을 단일 원장 테이블에서 차원(`scoreType`, `problemType`)으로 흡수했다. 

> **"복잡한 계산과 정합성 보장은 점수 적립 시점에 완벽하게 끝내두고, 읽는 쪽(랭킹/스코어보드)은 가볍게 유지한다."**

이 원칙이 프로젝트의 핵심 설계 축이 되었다.

## 런타임에서 터진 5가지 정합성 버그와 중앙 엔진 수술

원장 모델로 전환한 후에도 실시간 운영 환경에서 데이터 정합성이 어긋나는 문제들이 터져 나왔다. 원인은 점수 갱신 로직이 유저, 문제, 제출 각 테이블의 라이프사이클 훅에 산발적으로 흩어져 있었기 때문이었다. 분산된 부수효과들을 한데 모아 5가지 핵심 버그를 전수 수술했다.

### 1. 정답 추가 시 소급 누락 버그
누군가 정답을 맞히면 문제 배점이 낮아져야 한다. 그런데 스코어보드를 확인해보니 **방금 정답을 맞힌 유저의 행만 낮아진 점수로 저장되고, 이전에 푼 유저들의 행은 과거의 비싼 점수 그대로 방치**되어 전체 점수 인플레이션이 발생하고 있었다.

새 정답을 원장에 기록한 직후, 해당 문제의 기존 정답자 원장 전체를 새 배점으로 즉시 일괄 동기화하도록 수정했다.

```js
// 1) 신규 정답자 원장 기록
await scoreboard.create({
  data: { userId, problemId, scoreType: 'solve', problemType: 'personal', score: solveScore },
});

// 2) 해당 문제를 이미 푼 모든 기존 정답자의 원장 점수를 새 배점으로 일괄 소급
await scoreboard.updateMany({
  where: { problemId, problemType: 'personal', scoreType: 'solve' },
  data:  { score: solveScore },
});
```

### 2. 제출 삭제 시 옆 사람 점수 오삭제 버그
참가자가 제출 내역을 취소하거나 삭제할 때 원장에서 해당 점수를 지워야 했는데, 삭제 조건(`where`)에 유저 식별자가 누락되어 **엉뚱한 다른 유저의 정상 정답 행이 삭제되는 황당한 버그**가 있었다.

복합 고유 키(`userId + problemId + scoreType`)를 `where` 절에 정밀하게 강제하여 인접 유저의 원장이 휩쓸리는 현상을 원천 차단했다.

### 3. 분산된 부수효과 스파게티의 중앙 일원화
승인 대기(`waiting`) 중인 문제가 점수를 미리 적립하거나, 문제를 삭제했는데 연관 점수가 원장에 잔류하는 등 부수효과들이 제각각 돌고 있었다. 

원인을 추적해보니 점수 로직이 여러 모델의 훅에 파편화되어 실행 순서를 제어할 수 없었기 때문이었다. 파편화된 훅을 전부 제거하고, **모든 점수 변동 사건이 단 하나의 중앙 트랜잭션 함수(`recalculateScore`)를 통과하도록 일원화**했다.

### 4. 에러를 던지지 않는 침묵의 버그 (관리자 계정 모수 오염)
운영 중 참가자들로부터 "전체 점수가 계산 공식보다 미세하게 높다"는 제보가 들어왔다. 스택 트레이스도, 빨간색 에러 로그도 전혀 발생하지 않던 상황이었다.

추적 결과, 전체 참가자 수를 계산하는 `totalUserCount`의 단순 `count()` 쿼리에 **테스트용 운영자/관리자 계정까지 모수에 포함**되어 분모와 분자가 모두 부풀려져 있었다. 모든 집계 쿼리에 `role = 'USER'` 필터를 엄격히 적용하여 관리자 모수를 완벽히 분리해냈다.

### 5. 팀전 기여도 차원 확장
개인전뿐 아니라 팀전 채점 요구사항이 추가되었을 때도, 기존 원장 구조의 진가가 드러났다. 팀장이 팀원의 기여도를 등급(A~F, 100%~0%)으로 입력하면 배점을 비율대로 나누어 적립하는 구조였는데, 개인전 로직을 복사하지 않고 단일 원장에 `problemType: 'team'`과 `grade` 차원만 얹어 동일한 채점 파이프라인으로 흡수했다.

## 결과

실시간 동적 채점 시스템의 정합성이 완벽하게 맞춰졌다.

* 정답자가 늘어나면 선행 정답자들의 점수가 실시간으로 공정하게 소급 차감된다.
* 제출 삭제나 문제 취소 시에도 다른 유저의 점수가 훼손되지 않는다.
* 관리자 계정 격리로 점수 수식의 수학적 무결성을 확보했다.
* 실시간 랭킹과 마이페이지, 엑셀 출력은 원장 데이터를 단순 `SUM` 집계하는 것만으로 가볍고 빠르게 서빙되었다.

## 회고: 기술적 정합성을 넘어선 '점수의 공평함'

돌아보면 이 문제는 복잡한 알고리즘의 문제가 아니라, **도메인의 시간적 특성에 맞는 올바른 데이터 모델을 선택하는 문제**였다. 나눗셈 수식 자체는 처음부터 옳았다. 틀렸던 것은 과거를 소급하는 값을 '확정된 단일 합계 컬럼'으로 다루려 했던 초기 가정이었다. **나중 사건이 과거를 바꾸는 도메인에서는 반드시 이벤트 원장(Ledger)을 통해 변화의 궤적을 보존해야 한다.**

하지만 프로젝트가 끝난 뒤 가장 깊게 머리에 남은 것은 버그 수술보다 '이 점수 시스템이 참가자들에게 진정으로 공평하게 느껴질까?'라는 질문이었다.

동적 스코어링은 난이도에 따른 합당한 보상을 제공하지만, 자칫 1등과 후발 주자의 점수 격차가 걷잡을 수 없이 벌어져 참가자들이 조기에 의욕을 잃게 만들 위험도 안고 있다. 분모와 분자의 가중치를 어떻게 조절해야 끝까지 긴장감 넘치는 경쟁이 유지될지, 출제 보상과 풀이 보상의 균형을 어디에 맞춰야 생태계가 활성화될지 고민했던 경험은, **기술적인 데이터 정합성뿐만 아니라 유저가 체감하는 시스템의 공평함과 게임 경험까지 함께 고려하는 엔지니어링 시야**를 넓혀준 소중한 자산이 되었다.
