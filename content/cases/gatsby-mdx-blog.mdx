"블로그 글 하나 올릴 때마다 개발자를 불러야 하는 구조가 세상에서 제일 비효율적이다."

입사 초기, AI 솔루션 회사의 공식 홈페이지 및 기술 블로그 구축을 1인 프론트엔드로 맡았다. 회사 소개, 연구 프로젝트 아카이브, 채용, 그리고 블로그 섹션으로 구성된 웹사이트였다.

가장 큰 병목은 블로그였다. 디자이너와 기획자가 매주 멋진 아티클을 작성해 주었지만, 그것을 웹 화면에 띄우는 작업은 매번 나의 몫이었다. 원고를 전달받아 React JSX 마크업으로 일일이 옮겨 적고, 이미지를 폴더에 맞춘 뒤 배포를 돌리는 일련의 과정에 매번 두 명의 리소스가 낭비되고 있었다.

## 1. 문제: 콘텐츠가 코드 안에 갇혀 있을 때 생기는 비용

콘텐츠가 프론트엔드 코드베이스 안에 하드코딩되어 있으면, 글자 하나를 고치거나 새 글을 발행할 때마다 무조건 개발자의 손을 거쳐야 한다.

처음에는 새 글이 올 때마다 컴포넌트 파일을 하나씩 추가했다. 서너 개까지는 버틸 수 있었지만, 글이 수십 개씩 쌓여가는 블로그의 특성상 이는 지속 불가능했다. 비개발자 작성자가 코드를 직접 건드리지 않고도 글을 발행할 수 있도록, **코드와 콘텐츠를 완벽히 분리하는 시스템**이 절실했다.

## 2. 트레이드오프: 무거운 Headless CMS 대신 Gatsby + MDX 정적 생성

선택지는 두 가지였다:
1. **Headless CMS + 런타임 데이터 패칭**: Strapi나 WordPress 같은 별도 CMS 서버와 DB를 구축하여 런타임에 글을 불러온다.
2. **정적 사이트 생성(SSG) + MDX**: 마크다운 파일 기반으로 빌드 타임에 모든 페이지를 정적 HTML로 컴파일한다.

하루에 수만 건의 글이 올라오는 포털도 아니고, 트래픽이 폭증하는 환경도 아니었다. 단지 회사 소식을 전하는 홈페이지를 위해 별도의 CMS 서버와 데이터베이스를 띄우고 운영 비용을 지출하는 것은 전형적인 오버엔지니어링이었다.

**Gatsby와 MDX 기반의 정적 사이트 생성**(SSG)을 택했다. 글을 `content/<카테고리>/*.mdx` 파일로 저장해 두면, 빌드 타임에 GraphQL로 모든 노드를 긁어와 정적 HTML 페이지로 구워내는 구조다.

## 3. 구현: 비개발자 친화적인 MDX 파이프라인

`gatsby-node.js`에서 빌드 시 모든 MDX 파일을 순회하며 파일 경로로부터 `slug`와 카테고리를 자동 추출하고 동적 페이지를 생성하도록 구성했다:

```js
// gatsby-node.js — MDX 파일 하나당 독립된 정적 페이지 자동 생성
result.data.allMdx.edges.forEach(({ node }) => {
  createPage({
    path: node.fields.slug,
    component: path.resolve(`./src/components/posts-page-layout.js`),
    context: { id: node.id },
  });
});
```

MDX의 가장 큰 장점은 평범한 마크다운 문법으로 글을 쓰면서도, 필요한 지점에 미리 만들어둔 인터랙티브 React 컴포넌트(차트, CTA 버튼, 콜아웃)를 자유롭게 끼워 넣을 수 있다는 점이었다.

### 코드가 아닌 '문서'로 시스템을 비개발자에게 쥐여주다
정작 시스템을 만드는 것보다 중요한 것은 **비개발자가 이 시스템을 두려움 없이 사용할 수 있게 만드는 것**이었다.

README에 비개발자를 위한 상세한 콘텐츠 작성 가이드를 직접 작성했다:
- Frontmatter 메타데이터(`title`, `author`, `categories`, `date`)의 표준 작성법
- 이미지 상대 경로(`./images/filename.png`) 네이밍 규칙
- 주의사항: *HTML 태그를 닫지 않고 문법을 깨뜨리면 빌드가 실패하여 글이 보이지 않습니다*와 같은 실제 실수 사례 기반의 가이드라인

## 결과

* **콘텐츠 발행의 개발자 의존도 제로화**: 디자이너와 기획자가 마크다운 파일 하나와 이미지만 깃 저장소에 올리면 즉시 글이 게시되는 자립적인 워크플로우를 완성했다.
* **배포 파이프라인의 진화**:
  - 초기: CI 환경이 없어 빌드 결과물(`public/`)을 깃에 올려 서버에서 `git pull`로 배포
  - 중기: PM2 기반의 정적 서버 셀프 호스팅
  - 최종: Git 푸시 시 자동으로 빌드·배포되는 Netlify CI/CD 파이프라인으로 전환하여 "Push = 배포" 완성

## 회고: 최고의 시스템은 '나를 배제할 수 있는 시스템'이다

이 프로젝트에서 만든 가장 가치 있는 결과물은 복잡한 프론트엔드 코드가 아니라, **디자이너와 기획자가 스스로 글을 발행할 수 있게 만들어준 친절한 매뉴얼과 인터페이스**였다.

내가 자리에 없어도, 다른 업무에 집중하고 있어도 시스템이 스스로 굴러가도록 만드는 것 — **나(개발자)라는 병목을 시스템에서 스스로 빼버리는 것**이 엔지니어링이 조직에 기여할 수 있는 가장 큰 생산성 혁신임을 입사 초기에 깊이 깨달은 뜻깊은 경험이었다.
