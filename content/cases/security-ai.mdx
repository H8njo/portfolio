"그냥 입력창 몇 개 모아둔 폼 마법사(Wizard)겠지."

AI 기반 보안관제 시스템의 어드민 화면을 처음 마주했을 때 든 생각이었다. 보안 관제사가 파이썬 코드 한 줄 작성하지 않고도 GUI만으로 네트워크 이상 징후를 탐지하는 머신러닝(ML) 모델을 직접 학습시키는 화면이었다. 하지만 가벼운 마음으로 시작한 이 화면은, 이번 프로젝트에서 가장 깊게 고민하고 가장 오래 붙들린 최대 난제의 화면이 되었다.

## 문제: 5개 대단계 밑에 하위 갈래가 얽힌 2층 계층 구조

마법사의 뼈대는 5개의 큰 단계로 이루어져 있었다:
1. **데이터 선택** → 2. **특징 추출** → 3. **알고리즘 학습** → 4. **모델 검증/테스트** → 5. **최종 요약 및 실행**

하지만 단순한 5단계 선형 구조가 아니었다. 첫 번째 '데이터 선택' 단계만 해도, 신규 수집 / 기수집 데이터 / 기학습 데이터 / 추천 데이터 중 무엇을 고르느냐에 따라 뒤따르는 화면이 4갈래로 완전히 갈라졌다. 실제 사용자의 이동 경로는 `1-1 → 1-2 → 1-3 … 2-1 → 2-2`처럼 **큰 단계(Step) 밑에 작은 단계(Substep)가 매달린 2층 계층 구조**였다.

단순한 폼 화면처럼 보였지만, 본질은 백엔드에서 몇 분에서 몇 시간씩 도는 **거대한 분산 ML 파이프라인을 브라우저에서 통째로 조작하는 콘솔**이었던 셈이다.

### 화면을 무너뜨리는 3가지 상태 딜레마

사용자는 이 2층 단계를 자유롭게 앞뒤로 오간다. 1-1에서 데이터를 고르고 3단계까지 갔다가, "데이터를 잘못 골랐네" 하고 다시 1-1로 돌아오기도 하고, 뒤로가기를 누르거나, 링크를 북마크해 두고 다음 날 다시 들어오기도 한다.

이 과정에서 3가지 치명적인 문제가 얽혀 있었다:

1. **위치 보존의 딜레마**: 새로고침 한 번에 1-1 첫 화면으로 튕겨 나가면 사용자는 처음부터 모든 설정을 다시 해야 한다.
2. **깊은 중첩 설정의 보존**: 3단계 알고리즘 설정만 해도 옵티마이저, 탐색 방식, K-Fold 교차검증 횟수, 학습 비율 등 수십 개의 복잡한 객체 트리가 중첩되어 있다. 앞 단계로 돌아갔다 와도 이 설정값들이 유실 없이 살아 있어야 한다.
3. **캐스케이딩 무효화 (Cascading Invalidation)**: 1단계 데이터를 다른 데이터셋으로 갈아끼웠다면, 기존 데이터를 전제로 뽑아둔 2단계 특징 ID와 3단계 알고리즘 파라미터는 **즉시 무효화**(초기화)되어야 한다. 옛날 설정이 남아 있는 상태로 학습을 실행하면, 몇 시간 동안 비싼 GPU/CPU 워커가 엉뚱한 데이터로 학습을 헛돌리는 막대한 낭비가 발생한다.

흔히 쓰듯 `currentStep` 숫자 변수 하나로 관리했다가는 모든 정합성이 깨질 수밖에 없었다.

## 해결 1: 내비게이션은 URL에, 깊은 데이터는 Immer 리듀서에

서로 성격이 다른 두 상태를 한곳에 뭉쳐두지 않고 책임을 명확히 분리했다:

### 1. URL을 현재 위치의 단일 진실 공급원으로
보통 마법사의 현재 단계는 React의 `useState`로 들고 가기 쉽다. 하지만 컴포넌트 상태로 관리하면 새로고침 시 초기화되고, 브라우저 뒤로가기를 누르면 마법사 자체를 이탈해버린다.

그래서 **현재 위치(큰 단계와 작은 단계)를 React 상태가 아니라 URL 쿼리 파라미터에 완전히 위임**했다:

```js
// context.js — 현재 위치는 URL에서 순수하게 파생
const currentStep = Number(router.query.step) || 1;
const currentSubstep = router.query.substep;

const goToStep = ({ step, substep }) => {
  if (step === currentStep && substep === currentSubstep) return;
  const query = { step };
  if (substep) query.substep = substep; // 2층: 큰 단계 밑에 작은 단계
  router.push({ pathname: router.pathname, query });
};
```

`step`과 `substep`이 URL에 함께 실리므로, `1-3` 단계에서 새로고침을 하거나 동료에게 URL 링크를 공유해도 정확히 그 자리로 즉시 복원된다. 화면은 그저 URL을 읽어서 렌더링하기만 하면 된다.

### 2. 복잡한 중첩 폼 데이터는 Immer Reducer로 관리
수십 개의 알고리즘 하이퍼파라미터처럼 URL에 담을 수 없는 깊은 설정값들은 `useImmerReducer`를 도입해 관리했다. `step3.algorithmOptions.explorationDatas.cvFold`처럼 깊숙이 중첩된 객체 트리도 불변성 갱신 실수 없이 직관적이고 안전하게 제어했다.

## 해결 2: 선행 단계가 바뀌면 후행 단계는 죽어야 한다 (캐스케이딩 무효화)

URL과 Immer 리듀서를 살아 숨 쉬는 상태 머신으로 연결하기 위해 엄격한 상태 전이 규칙을 세웠다:

1. **리소스 ID 발급 기반의 완료 판정**: 수집 데이터가 생성되면 `collectId`가, 특징 추출이 끝나면 `featureGroupId`가 서버에서 내려온다. 이 ID가 리듀서에 세팅되는 순간 해당 단계의 `completed: true` 플래그를 원자적으로 켰다.
2. **선행 변경 시 후행 의존성 즉시 파기**:
   ```js
   case 'SET_COLLECT_ID':
     state.collectId = action.payload;
     state.step1.completed = !!action.payload;
     // 1단계 데이터가 바뀌었으므로, 옛 데이터에 기대던 2·3단계 상태를 원천 무효화
     state.featureGroupId = null;
     state.step2.completed = false;
     state.algorithmId = null;
     state.step3.completed = false;
     break;
   ```
3. **누락된 단계의 시각적 에러 경고**: 상단 내비게이션 바에서 이전 단계가 미완료 상태(`completed: false`)인데 다음 단계로 진입을 시도하면 즉시 `error` 뱃지와 경고 문구를 띄워 설정 누락을 방지했다.

## 해결 3: 5글자로 압축한 비동기 분산 파이프라인의 거울

학습 버튼을 누른다고 결과가 즉시 나오지 않는다. 각 단계가 완료될 때까지 화면은 "지금 백엔드에서 무슨 일이 일어나고 있는지"를 정직하게 보여주어야 했다.

모델 학습 파이프라인은 **Crawl(수집) → Feature(특징) → Normalize(정규화) → Train(학습) → Test(검증)** 5단계를 거치며, 각 단계는 `S`(대기), `R`(실행중), `C`(완료), `E`(에러)의 4개 상태를 갖는다.

백엔드는 이 복잡한 상태를 5글자의 컴팩트한 progress 문자열(예: `C-R, F-S...`)로 합성해 내려주었고, 프론트엔드는 이를 폴링하여 실시간 진행률 게이지로 시각화했다.

```sql
concat(
  NVL(CONCAT('C', crawl_step), ''),     -- Crawl (수집)
  NVL(CONCAT('F', feature_step), ''),   -- Feature (특징추출)
  NVL(CONCAT('N', normalize_step), ''), -- Normalize (정규화)
  NVL(CONCAT('R', train_step), ''),     -- tRain (학습)
  NVL(CONCAT('T', test_step), '')       -- Test (검증)
) as progress_step
```

특히 수집·특징추출은 **Java 워커**가, 정규화·학습·검증은 **Python 워커**(Celery/RabbitMQ)가 처리하는 이종 분산 환경이었는데, 프론트엔드는 이 5글자 상태 조합만으로 어느 워커 큐에 작업이 적재되어 있는지를 대시보드에 정확하게 분류해 보여주었다.

## 해결 4: Elasticsearch의 함정 — 왜 기간 필터를 걸었는데 전체가 나올까?

마법사의 데이터 수집 범위 설정에는 Elasticsearch 기반의 GUI 쿼리 빌더가 들어갔다. 그런데 검색 폼에서 분명 특정 기간(range) 조건을 걸었는데도 필터가 전혀 먹지 않고 전체 데이터가 조회되는 기이한 버그가 발생했다.

원인은 Elasticsearch의 `bool` 쿼리 메커니즘에 있었다:

```js
// 잘못된 코드: range가 should 절에 들어가 있음
query.bool.should.push({ range: { time: { gte, lte } } });
```

Elasticsearch에서 `must` 조건이 하나라도 존재하는 순간, `should` 절은 필수 필터가 아니라 **점수(Score) 가산용 옵션**으로 격하된다. 즉, 기간 조건이 '있으면 점수를 더 주고, 없어도 통과'되는 무용지물이 되었던 것이다.

이를 `bool.must`(또는 점수 계산이 필요 없는 캐시 친화적인 `bool.filter`)로 재배치하여 기간 필터링이 의도대로 정확하게 작동하도록 해결했다.

## 결과

* **견고한 2층 마법사 UX**: 새로고침, 브라우저 뒤로가기, URL 공유 등 어떤 사용자 조작에도 1-3단계 위치와 설정값이 안전하게 유지되어 관제사의 온보딩 피로도를 획기적으로 낮췄다.
* **학습 자원 낭비 차단**: 선행 단계 변경 시 후행 의존성을 리듀서에서 즉시 무효화하여, 무효한 데이터로 수 시간 동안 비싼 GPU 학습 워커를 헛돌리는 사고를 사전에 완벽히 차단했다.
* **분산 파이프라인의 실시간 가시성**: 5글자 상태 문자열 기반의 실시간 트래킹으로 장시간 소요되는 비동기 학습 과정의 투명성을 확보했다.

## 회고: 프론트엔드 화면은 거대한 시스템을 비추는 거울이다

처음에는 그저 폼 몇 개를 잘 배치하면 끝나는 UI 작업인 줄 알았다. 하지만 파고들수록 화면의 본질은 **백엔드에서 길게 도는 비동기 분산 파이프라인의 상태를 한 치의 오차 없이 정직하게 비추는 거울**이었다.

이 프로젝트를 거치며 몇 가지 단단한 엔지니어링 원칙이 몸에 배었다:
1. **단계가 있는 화면의 내비게이션 위치는 반드시 URL에 둔다.** 컴포넌트 내부 state에 두는 순간 새로고침과 딥링크 앞에서 무너진다.
2. **데이터 의존성에 따른 상태 무효화는 UI가 아니라 상태 관리 계층(리듀서)에 못 박는다.** 화면에서만 숨기면 내부 메모리에선 옛 참조가 살아남아 언젠가 대형 버그로 터진다.

무엇보다 시작할 땐 생소했던 머신러닝 파이프라인의 생김새와 Elasticsearch의 검색 엔진 메커니즘을 어깨너머로 배우고 깊이 파고들며, 단순한 화면 구현을 넘어 시스템 전체를 조망하는 풀스택 엔지니어로 성장할 수 있었던 뜻깊은 프로젝트였다.
