가장 무서운 에러는 빨간 글씨로 터지는 에러가 아니다. 아무 일도 일어나지 않는 에러다.

수업 관리 웹 애플리케이션을 운영하던 중 기묘한 버그 제보가 들어왔다. 사용자가 "시험지 생성" 버튼을 눌렀는데 화면에 아무런 반응이 없고, 로딩 스피너만 무한히 돌거나 버튼이 잠겨버린다는 것이었다. 브라우저 개발자 도구를 열어봐도 빨간색 에러 로그 한 줄 찍히지 않았다. 서버에는 요청이 도달하지 않았거나 500 응답이 찍혔는데, 프론트엔드는 마치 아무 일도 없었다는 듯 침묵하고 있었다.

원인을 찾으려 코드를 파고들기 시작했을 때, 코드베이스 전반에 걸쳐 조용히 숨어 있던 비동기 안티패턴과 파편화된 에러 처리들이 민낯을 드러냈다.

## 문제

에러가 허공으로 증발하고 있었다.

코드를 열어보니 크게 세 가지 문제가 얽혀 있었다.

### 1. `try` 블록 안의 `.then()` 안티패턴
가장 결정적인 원인은 `async/await`와 `.then()` 체이닝의 기형적인 혼용이었다:

```ts
// AS-IS: try는 동기적으로 끝나고, .then 내부의 에러는 허공으로 날아간다
try {
  fetchExamData(paperId).then((res) => {
    const parsed = parseQuestions(res.data); // 여기서 런타임 에러 발생!
    setQuestions(parsed);
  });
} catch (e) {
  // .then은 마이크로태스크 큐에서 비동기로 실행되므로
  // 이미 실행이 끝난 try-catch는 이 에러를 절대 잡지 못한다.
  showToast('데이터를 불러오지 못했습니다.');
}
```

`try` 블록은 `fetchExamData` 프로미스를 생성하자마자 동기적으로 실행을 끝내버린다. 나중에 네트워크 응답이 와서 `.then` 콜백 안에서 파싱 에러가 터졌을 때, 호출 스택에 `try...catch`는 이미 존재하지 않는다. 결국 이 에러는 잡히지 않은 채(Unhandled Promise Rejection) 콘솔에도 제대로 기록되지 않고 증발했다.

### 2. 에러 삼킴(Error Swallowing)과 무한 로딩
어떤 코드는 에러를 잡긴 했지만, 무책임하게 삼켜버리고 있었다:

```ts
// AS-IS: 에러를 삼키고 로딩을 해제하지 않음
setIsLoading(true);
try {
  await submitForm(data);
} catch (e) {
  console.log(e); // 콘솔에만 대충 찍고 종료
  // setIsLoading(false) 누락 → 버튼이 영원히 비활성화됨
}
```

에러가 발생했을 때 로딩 상태를 풀어주지 않으니, 사용자는 버튼이 멈춘 줄 알고 새로고침을 누르며 데이터를 날려야 했다.

### 3. 처리 방식의 극단적 파편화
누구는 `alert()`를 띄우고, 누구는 전역 토스트를 띄우고, 누구는 빈 배열을 조용히 반환했다. 프로젝트 내에 "에러를 어떻게 다룰 것인가"에 대한 합의된 규칙이 전혀 없었다.

## 트레이드오프 결정: Global vs Local 2계층 분류 체계

"모든 에러를 한곳에서 잡을 수도 없고, 모든 에러를 개별 컴포넌트가 알아서 처리하게 둬서도 안 된다."

에러의 성격에 따라 처리 책임을 명확히 가르는 2단계 분류 체계를 세웠다:

```text
┌─────────────────────────────────────────────────────────┐
│                    에러 발생 시 판별                     │
├───────────────────────────┬─────────────────────────────┤
│  Local Error (로컬 소비)   │  Global Error (상위 전파)   │
├───────────────────────────┼─────────────────────────────┤
│ • 인풋 폼 유효성 검증 실패  │ • 401 세션 만료             │
│ • 특정 위젯의 사소한 실패   │ • 403 접근 권한 부족         │
│ • 인라인 피드백이 필요한 경우│ • 500 서버 내부 오류 / 장애 │
│                           │ • 네트워크 단절             │
├───────────────────────────┼─────────────────────────────┤
│  컴포넌트 로컬 상태로 소비   │  throw로 상위 전파          │
│  (인라인 에러 문구 표시)     │  (전역 핸들러/토스트/모달)   │
└───────────────────────────┴─────────────────────────────┘
```

1. **Local Error**: 폼 입력 오류처럼 사용자가 그 자리에서 수정할 수 있는 에러는 컴포넌트 내부에서 잡아 인라인 메시지로 소비한다.
2. **Global Error**: 인증 만료, 서버 다운, 네트워크 끊김처럼 개별 화면이 어찌할 수 없는 인프라 에러는 **어설프게 잡지 말고 `throw`로 상위로 던진다.** 상위 전역 핸들러와 `ErrorBoundary`가 공통 토스트, 로그인 모달, 또는 재시도 화면으로 일원화하여 처리한다.

## 접근

### 1. 공용 에러 핸들링 모듈 구축 (`@sling-inc/error-handler`)
모노레포(Turborepo) 환경의 이점을 살려, 에러 처리 로직을 공용 패키지로 모듈화했다.

- **UI Safe Error**: 사용자에게는 `Cannot read properties of undefined` 같은 흉측한 스택 대신 정제된 문구("일시적인 네트워크 오류가 발생했습니다. 다시 시도해 주세요")를 보여준다.
- **에러 지문(Fingerprint) 트래킹**: 개발자 콘솔과 Sentry 로깅에는 고유 `errorId`, 발생 API URL, 요청 파라미터, 컴포넌트 스택을 함께 묶어 기록했다. 덕분에 사용자가 "생성이 안 돼요"라고 문의하면 `errorId` 하나로 당시의 모든 컨텍스트를 즉시 추적할 수 있게 됐다.

```ts
// 에러 전파와 지문 부여를 표준화한 공용 유틸
export function handleApiError(error: unknown, context?: ErrorContext) {
  const appError = normalizeError(error, context);
  
  if (appError.isGlobal) {
    // Sentry 지문 로깅 + 전역 에러 이벤트 방출
    reportToMonitoring(appError);
    globalErrorEmitter.emit('GLOBAL_ERROR', appError);
    return;
  }
  
  // 로컬 에러는 호출자에게 다시 던져 컴포넌트가 직접 처리하게 위임
  throw appError;
}
```

### 2. 비동기 린트 규칙 강제
사람의 주의력에 기대지 않고, 비동기 실수를 CI 빌드 단계에서 원천 차단하도록 ESLint 규칙을 추가했다:
- `@typescript-eslint/no-floating-promises`: `await`나 `.catch()` 없이 떠도는 프로미스 금지
- `@typescript-eslint/return-await`: `try...catch` 내부에서 `return await` 없이 프로미스를 던지는 실수 차단

### 3. 최후의 안전망 구축
코드에서 놓친 예외가 있더라도 브라우저 레벨에서 증발하지 않도록 `window.addEventListener('unhandledrejection')`를 걸어, 미처리된 비동기 에러까지 전역 로깅으로 포획했다.

## 문화와 리더십: 문서화와 전사 테크톡 발표

기술적인 해결책을 만들었지만, 팀원들이 쓰지 않으면 무용지물이었다.

1. **원리 중심의 가이드 문서화**: "이렇게 쓰세요"라는 단순 규칙 나열 대신, **"왜 try 안의 .then이 에러를 삼키는지"**, **"이벤트 루프와 마이크로태스크 큐에서 무슨 일이 벌어지는지"**를 도식화한 문서를 작성했다.
2. **사내 테크 세미나 발표**: 실제 발생했던 "침묵의 에러" 사례를 시연하고, Global/Local 2계층 에러 핸들링 아키텍처를 공유했다.

발표 이후 팀원들의 적극적인 공감을 얻어 해당 아키텍처가 전사 프론트엔드 표준으로 채택되었고, 내가 공용 에러 핸들링 모듈의 메인테이너를 맡아 전사 코드베이스로 확산시켰다.

## 결과

- **무반응 버그 0건화**: 비동기 안티패턴과 에러 삼킴이 사라지며, 사용자가 버튼을 눌렀을 때 아무 피드백 없이 멈추는 현상이 완전히 소거됐다.
- **디버깅 리드타임 대폭 단축**: 에러 발생 시 고유 에러 지문과 API 컨텍스트가 Sentry에 완벽히 기록되어, 과거 반나절씩 걸리던 원인 재현 및 디버깅 시간이 10~20분 이내로 줄었다.
- **개발 생산성 향상**: 새 화면이나 API를 연동할 때 "에러를 어떻게 잡을지" 매번 고민할 필요 없이, 표준화된 모듈을 통해 일관된 에러 처리를 즉시 적용할 수 있게 됐다.

## 회고

에러 핸들링의 핵심은 **"에러가 안 나게 숨기는 것"이 아니라 "에러를 예측 가능한 방식으로 투명하게 드러내는 것"**이다.

비동기 문법의 작은 부주의가 어떻게 전체 애플리케이션을 침묵의 늪에 빠뜨리는지 목격했고, 이를 시스템적인 아키텍처와 린트 룰, 그리고 팀원들의 공감대를 형성하는 테크톡을 통해 문화로 풀어낸 값진 경험이었다.
