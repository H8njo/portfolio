{/* NDA 안전: 수업 관리 웹 애플리케이션. */}

가장 무서운 에러는 화면에 빨간 글씨로 굉음을 내며 터지는 에러가 아니다. 아무런 일도 일어나지 않는 **침묵의 에러**다.

수업 관리 웹 애플리케이션을 운영하던 중 기묘한 버그 제보가 들어왔다. 사용자가 "시험지 생성" 버튼을 눌렀는데 화면에 아무런 반응이 없고, 로딩 스피너만 무한히 돌거나 버튼이 영구히 잠겨버린다는 것이었다.

브라우저 개발자 도구를 열어봐도 콘솔에 빨간색 에러 로그 한 줄 찍히지 않았다. 서버 로그를 확인해 보니 백엔드는 분명 500 에러를 뱉었는데, 프론트엔드는 마치 아무 일도 없었다는 듯 평온하게 침묵하고 있었다.

원인을 찾기 위해 코드를 파고들기 시작했을 때, 자바스크립트 비동기 런타임의 가장 끔찍한 함정을 마주했다.

## 1. 문제: 겉보기엔 완벽했던 코드의 배신

호출부 컴포넌트의 코드는 교과서처럼 완벽해 보였다:

```ts
// 호출부 컴포넌트: 정석대로 try-catch와 await를 썼다
try {
  setIsLoading(true);
  await createExamPaper(data); // ⚠️ 서버는 500 에러를 뱉었는데?
} catch (e) {
  // ❌ 여기가 절대로 실행되지 않는다!
  showErrorModal('시험지 생성에 실패했습니다.');
} finally {
  setIsLoading(false);
}
```

호출하는 쪽에선 아무리 코드를 뜯어봐도 `try...catch`와 `await`를 정석대로 썼다. 서버가 500 에러를 뱉었으니 당연히 `catch` 블록으로 들어가 에러 모달이 떠야 했다. 하지만 `catch`문은 완전히 무시되었고, 코드는 마치 정상 응답을 받은 양 통과해버렸다.

원인은 `createExamPaper` 안의 안의, **3단계 아래 깊숙한 곳에 숨어 있던 레거시 유틸리티 함수**에 있었다:

### ① 하위 계층의 `.then().catch()` 에러 삼킴
```ts
// 3단계 아래 깊숙한 곳의 레거시 유틸 함수
function requestApi(url, options) {
  return fetch(url, options)
    .then((res) => {
      if (!res.ok) throw new Error('API Fail');
      return res.json();
    })
    .catch((err) => {
      console.error('API Error:', err);
      // ⚠️ 아무것도 re-throw하지 않고 종료!
      // -> Promise가 에러가 아니라 '성공(fulfilled, undefined)'으로 종결된다.
    });
}
```

자바스크립트 Promise의 `.catch()`는 내부에서 다시 `throw`하지 않으면 **에러가 정상 복구된 것으로 간주하여 `undefined`를 resolve하는 정상 Promise를 반환**한다.

결국 상위 컴포넌트는 하위에서 에러가 터졌다는 사실조차 전달받지 못한 채 `await`를 성공적으로 통과했고, `catch`문은 영원히 실행되지 않는 죽은 코드가 되어 있었던 것이다.

### ② `try` 블록 안에서 `await` 없는 `.then()` 호출
어떤 곳은 `try` 블록 안에서 `await` 없이 `.then()`을 비동기로 돌리고 있었다:

```ts
// AS-IS: try는 동기 종료되고, .then 내부의 에러는 허공(Unhandled Rejection)으로 증발
try {
  fetchUserData().then((res) => {
    const parsed = parseProfile(res.data); // 런타임 에러 발생!
    setUser(parsed);
  });
} catch (e) {
  // .then은 마이크로태스크 큐에서 비동기로 실행되므로 이미 끝난 try-catch는 못 잡는다
}
```

### ③ finally 누락과 무한 로딩
어떤 코드는 `finally` 없이 `catch (e) { console.log(e); }`로 에러를 삼켜버려 `setIsLoading(false)`가 호출되지 않아 버튼이 영구히 잠겼고, 누구는 `alert()`, 누구는 빈 배열을 반환하는 등 처리 방식마저 극단적으로 파편화되어 있었다.

## 2. 아키텍처: Global vs Local 2계층 에러 분류 체계

"모든 에러를 전역에서 잡을 수도 없고, 모든 에러를 개별 컴포넌트가 알아서 처리하게 둬서도 안 된다."

에러의 성격과 복구 주체에 따라 책임을 명확히 가르는 **2단계 에러 분류 체계**를 정립했다:

- **Local Error (컴포넌트 로컬 소비)**:
  - **발생 사례**: 인풋 폼 유효성 검증 실패, 특정 위젯의 사소한 조회 실패 등 인라인 피드백이 필요한 경우.
  - **처리 방식**: 컴포넌트 로컬 상태로 소비하여 폼 필드 아래에 붉은 안내 문구를 노출하고 사용자 수정을 유도.
- **Global Error (상위 전파 및 일원화)**:
  - **발생 사례**: 401 세션 만료, 403 권한 부족, 500 서버 장애, 네트워크 단절.
  - **처리 방식**: 컴포넌트가 어설프게 삼키지 않고 상위로 `throw`하여, 전역 에러 핸들러와 `ErrorBoundary`가 공통 토스트, 로그인 모달, 또는 재시도 풀스크린 화면으로 일원화하여 대응.

## 3. 구현: 공용 에러 핸들링 모듈과 린트 안전망

### ① 공용 에러 핸들링 모듈 구축
모노레포(Turborepo) 공용 패키지로 에러 처리 파이프라인을 모듈화했다:

- **UI Safe Error**: 사용자에게는 `Cannot read properties of undefined` 같은 흉측한 스택 대신 "일시적인 네트워크 오류가 발생했습니다. 다시 시도해 주세요"와 같은 정제된 메시지를 노출.
- **에러 지문(Fingerprint) 트래킹**: Sentry와 개발자 콘솔 로깅에 고유 `errorId`, 요청 URL, 파라미터, 컴포넌트 스택을 묶어 기록하여 사용자가 "생성이 안 돼요"라고 문의하면 1초 만에 원인을 추적할 수 있도록 개선.

```ts
// 에러 전파와 지문 부여를 표준화한 공용 유틸
export function handleApiError(error: unknown, context?: ErrorContext) {
  const appError = normalizeError(error, context);
  
  if (appError.isGlobal) {
    reportToMonitoring(appError); // Sentry 로깅
    globalErrorEmitter.emit('GLOBAL_ERROR', appError); // 전역 토스트/모달 방출
    return;
  }
  
  // 로컬 에러는 호출자에게 re-throw하여 컴포넌트가 직접 처리하게 위임
  throw appError;
}
```

### ② 비동기 린트 룰셋과 브라우저 최후의 안전망
- `@typescript-eslint/no-floating-promises`: `await`나 `.catch()` 없이 떠도는 프로미스 빌드 단계 차단.
- `@typescript-eslint/return-await`: `try...catch` 내부에서 `return await` 없이 프로미스를 던지는 실수 방지.
- `window.addEventListener('unhandledrejection')`를 등록하여, 코드에서 미처 잡지 못한 비동기 에러까지 최종 포획.

## 4. 문화와 리더십: 사내 세미나와 점진적 프로세스

기술적인 해법을 만들었지만, 팀원들의 공감대 없이는 유지될 수 없었다:

1. **사내 테크 세미나 발표**: 실제 발생했던 "침묵의 에러" 사례를 직접 시연하고, 이벤트 루프와 마이크로태스크 큐 관점에서 왜 `.then().catch()`가 위험한지 원리를 설명했다. 팀원들의 깊은 공감을 이끌어내며 전사 프론트엔드 표준으로 공식 채택되었다.
2. **PR 템플릿 체크리스트 장치**: 수백 개의 레거시 코드를 한 번에 바꾸는 빅뱅 방식 대신, 스프린트 단위로 점진적 전환을 합의했다. GitHub PR 템플릿에 `[ ] 에러 핸들링 표준(Global/Local) 확인` 체크리스트를 심어, 리뷰 과정에서 자연스럽게 에러 누수를 교정해 나갔다.

## 결과

* **핵심 플로우 무한 로딩 정상화**: 시험지 생성, 수업 개설 등 주요 비즈니스 모듈의 침묵하던 비동기 버그를 전면 박멸했다.
* **디버깅 리드타임 극적 단축**: 고유 에러 지문과 API 컨텍스트 기록을 통해, 과거 반나절 이상 소요되던 원인 분석 및 재현 시간이 10~20분 이내로 대폭 줄었다.
* **신규 개발 생산성 및 전사 표준 정착**: 신규 기능 개발 시 에러 처리에 대한 고민 없이 표준 패키지로 즉시 대응할 수 있게 되었고, PR 템플릿 체크리스트를 통해 코드리뷰 단계에서 에러 누수를 원천 방어했다.

## 회고: 에러는 숨기는 것이 아니라 정직하게 드러내는 것이다

나는 에러가 나는 것을 두려워하지 않는다.

정해진 규칙대로 흘러가지 않을 때 가차 없이 에러를 뱉어내는 컴퓨터의 정확함은, 시스템의 결함을 발견하고 소프트웨어의 완성도를 한 단계 끌어올릴 수 있는 가장 정직한 기회다.

반대로 에러가 터지는 것이 두려워 `catch`문으로 어설프게 덮어두거나 조용히 삼켜버리면, 나중에 걷잡을 수 없는 거대한 재앙으로 되돌아온다. 화면은 멈췄는데 에러 로그조차 남지 않고, 사용자는 데이터를 날리며, 개발자는 깜깜이 디버깅에 갇히게 된다.

**"에러 핸들링의 본질은 에러를 덮어 숨기는 것이 아니라, 컴퓨터가 정직하게 알려준 신호를 제어 가능한 방식으로 안전하게 드러내고 복구하는 것."** 비동기 문법의 작은 부주의를 파고들어 시스템과 프로세스로 이를 풀어낸 값진 경험이었다.
