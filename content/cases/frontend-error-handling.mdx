가장 무서운 에러는 빨간 글씨로 터지는 에러가 아니다. 아무 일도 일어나지 않는 에러다.

수업 관리 웹 애플리케이션을 운영하던 중 기묘한 버그 제보가 들어왔다. 사용자가 "시험지 생성" 버튼을 눌렀는데 화면에 아무런 반응이 없고, 로딩 스피너만 무한히 돌거나 버튼이 잠겨버린다는 것이었다. 브라우저 개발자 도구를 열어봐도 빨간색 에러 로그 한 줄 찍히지 않았다. 서버에는 500 에러가 분명히 발생했는데, 프론트엔드는 마치 아무 일도 없었다는 듯 침묵하고 있었다.

원인을 찾으려 코드를 파고들기 시작했을 때, 프론트엔드 비동기 런타임의 가장 끔찍한 함정을 마주했다.

## 문제

호출부의 코드는 교과서처럼 완벽해 보였다:

```ts
// 호출부 컴포넌트: 정석대로 try-catch와 await를 썼다
try {
  setIsLoading(true);
  await createExamPaper(data); // ⚠️ 서버는 500 에러를 뱉었는데?
} catch (e) {
  // ❌ 여기가 절대로 실행되지 않는다!
  showErrorModal('시험지 생성에 실패했습니다.');
} finally {
  setIsLoading(false);
}
```

호출하는 쪽에선 아무리 코드를 뜯어봐도 `try...catch`와 `await`를 정석대로 썼다. 서버는 500 에러를 뱉었으니 분명 `catch` 블록으로 들어가 에러 모달이 떠야 했다. 하지만 `catch`문은 완전히 무시되었고, 코드는 마치 정상 응답을 받은 양 통과해버렸다.

원인은 **`createExamPaper` 안의 안의, 몇 단계 아래 하위 계층 함수**에 숨어 있었다.

### 1. 하위 계층의 `.then().catch()` 에러 삼킴
하위 API 요청 헬퍼 어딘가에서 `async/await`와 `.then().catch()`를 혼용하며 에러를 가로채고 있었다:

```ts
// 3단계 아래 깊숙한 곳의 레거시 유틸 함수
function requestApi(url, options) {
  return fetch(url, options)
    .then((res) => {
      if (!res.ok) throw new Error('API Fail');
      return res.json();
    })
    .catch((err) => {
      console.error('API Error:', err);
      // ⚠️ 아무것도 re-throw하지 않고 종료!
      // -> Promise가 에러가 아니라 '성공(fulfilled, undefined)'으로 종결된다.
    });
}
```

자바스크립트 Promise의 `.catch()`는 내부에서 다시 `throw`하지 않으면 **에러가 복구된 것으로 간주하여 `undefined`를 resolve하는 정상 Promise를 반환**한다.

결국 상위 컴포넌트는 하위에서 에러가 터졌다는 사실조차 전달받지 못한 채 `await`를 성공적으로 지나갔고, `catch`문은 영원히 실행되지 않는 죽은 코드가 되어 있었다.

### 2. `try` 블록 안에서 `await` 없는 `.then()` 호출
어떤 곳은 `try` 블록 안에서 `await` 없이 `.then()`을 비동기로 돌리고 있었다:

```ts
// AS-IS: try는 동기 종료되고, .then 내부의 에러는 허공(Unhandled Rejection)으로 증발
try {
  fetchUserData().then((res) => {
    const parsed = parseProfile(res.data); // 여기서 런타임 에러 발생!
    setUser(parsed);
  });
} catch (e) {
  // .then은 마이크로태스크 큐에서 비동기로 실행되므로 이미 끝난 try-catch는 못 잡는다
}
```

### 3. 에러 삼킴과 무한 로딩
어떤 코드는 `finally` 없이 `catch (e) { console.log(e); }`로 에러를 삼켜버려 `setIsLoading(false)`가 호출되지 않아 버튼이 영구적으로 잠겼고, 누구는 `alert()`, 누구는 빈 배열을 반환하는 등 처리 방식마저 극단적으로 파편화되어 있었다.

## 트레이드오프 결정: Global vs Local 2계층 분류 체계

"모든 에러를 한곳에서 잡을 수도 없고, 모든 에러를 개별 컴포넌트가 알아서 처리하게 둬서도 안 된다."

에러의 성격에 따라 처리 책임을 명확히 가르는 2단계 분류 체계를 세웠다:

```text
┌─────────────────────────────────────────────────────────┐
│                    에러 발생 시 판별                     │
├───────────────────────────┬─────────────────────────────┤
│  Local Error (로컬 소비)   │  Global Error (상위 전파)   │
├───────────────────────────┼─────────────────────────────┤
│ • 인풋 폼 유효성 검증 실패  │ • 401 세션 만료             │
│ • 특정 위젯의 사소한 실패   │ • 403 접근 권한 부족         │
│ • 인라인 피드백이 필요한 경우│ • 500 서버 내부 오류 / 장애 │
│                           │ • 네트워크 단절             │
├───────────────────────────┼─────────────────────────────┤
│  컴포넌트 로컬 상태로 소비   │  throw로 상위 전파          │
│  (인라인 에러 문구 표시)     │  (전역 핸들러/토스트/모달)   │
└───────────────────────────┴─────────────────────────────┘
```

1. **Local Error**: 폼 입력 오류처럼 사용자가 그 자리에서 수정할 수 있는 에러는 컴포넌트 내부에서 잡아 인라인 메시지로 소비한다.
2. **Global Error**: 인증 만료, 서버 다운, 네트워크 끊김처럼 개별 화면이 어찌할 수 없는 인프라 에러는 **어설프게 잡지 말고 `throw`로 상위로 던진다.** 상위 전역 핸들러와 `ErrorBoundary`가 공통 토스트, 로그인 모달, 또는 재시도 화면으로 일원화하여 처리한다.

## 접근

### 1. 공용 에러 핸들링 모듈 구축 (`@sling-inc/error-handler`)
모노레포(Turborepo) 환경의 이점을 살려, 에러 처리 로직을 공용 패키지로 모듈화했다.

- **UI Safe Error**: 사용자에게는 `Cannot read properties of undefined` 같은 흉측한 스택 대신 정제된 문구("일시적인 네트워크 오류가 발생했습니다. 다시 시도해 주세요")를 보여준다.
- **에러 지문(Fingerprint) 트래킹**: 개발자 콘솔과 Sentry 로깅에는 고유 `errorId`, 발생 API URL, 요청 파라미터, 컴포넌트 스택을 함께 묶어 기록했다. 덕분에 사용자가 "생성이 안 돼요"라고 문의하면 `errorId` 하나로 당시의 모든 컨텍스트를 즉시 추적할 수 있게 됐다.

```ts
// 에러 전파와 지문 부여를 표준화한 공용 유틸
export function handleApiError(error: unknown, context?: ErrorContext) {
  const appError = normalizeError(error, context);
  
  if (appError.isGlobal) {
    // Sentry 지문 로깅 + 전역 에러 이벤트 방출
    reportToMonitoring(appError);
    globalErrorEmitter.emit('GLOBAL_ERROR', appError);
    return;
  }
  
  // 로컬 에러는 호출자에게 다시 던져 컴포넌트가 직접 처리하게 위임
  throw appError;
}
```

### 2. 비동기 린트 규칙 강제
사람의 주의력에 기대지 않고, 비동기 실수를 CI 빌드 단계에서 원천 차단하도록 ESLint 규칙을 추가했다:
- `@typescript-eslint/no-floating-promises`: `await`나 `.catch()` 없이 떠도는 프로미스 금지
- `@typescript-eslint/return-await`: `try...catch` 내부에서 `return await` 없이 프로미스를 던지는 실수 차단

### 3. 최후의 안전망 구축
코드에서 놓친 예외가 있더라도 브라우저 레벨에서 증발하지 않도록 `window.addEventListener('unhandledrejection')`를 걸어, 미처리된 비동기 에러까지 전역 로깅으로 포획했다.

## 문화와 리더십: 테크 세미나와 PR 템플릿 장치

기술적인 해결책을 만들었지만, 실무에서 자연스럽게 쓰이지 않으면 무용지물이었다.

1. **원리 중심의 가이드 문서화**: 단순 규칙 나열 대신, **try 안의 .then이 왜 에러를 삼키는지**, 그리고 **이벤트 루프와 마이크로태스크 큐의 비동기 실행 흐름**을 도식화한 문서를 작성했다.
2. **사내 테크 세미나 발표**: 실제 발생했던 "침묵의 에러" 사례를 시연하고, Global/Local 2계층 에러 핸들링 아키텍처를 공유했다. 발표 이후 팀원들의 적극적인 공감을 얻어 해당 아키텍처가 전사 프론트엔드 표준으로 채택되었다.
3. **스프린트 기반 점진적 마이그레이션과 PR 템플릿 장치**: 수백 개에 달하는 기존 레거시 코드를 한 번에 다 뜯어고치는 빅뱅(Big-bang) 방식은 리스크가 너무 컸다. 대신 정규 스프린트를 진행하며 기능 수정이나 신규 개발이 있을 때마다 점진적으로 교체하기로 합의했다. 이를 시스템적으로 보장하기 위해 **GitHub PR 템플릿에 `[ ] 에러 핸들링 표준(Global/Local) 마이그레이션 확인` 체크리스트를 추가**했다. 작성자와 리뷰어가 코드 리뷰 시점에 에러 누수를 놓치지 않고 챙기도록 프로세스 안전장치를 만든 것이다.

## 결과

- **핵심 플로우의 크리티컬 오류 정상화**: 시험지 생성, 수업 등록 등 주요 비즈니스 모듈부터 점진적으로 계층형 에러 처리를 적용해, 화면이 멈추거나 침묵하던 크리티컬한 비동기 버그들을 하나씩 잡아내고 정상 작동하도록 개선했다.
- **디버깅 리드타임 대폭 단축**: 에러 발생 시 고유 에러 지문과 API 컨텍스트가 Sentry에 완벽히 기록되어, 과거 반나절씩 걸리던 원인 재현 및 디버깅 시간이 10~20분 이내로 줄었다.
- **개발 생산성 향상**: 새 화면이나 API를 연동할 때 "에러를 어떻게 잡을지" 매번 고민할 필요 없이, 표준화된 모듈을 통해 일관된 에러 처리를 즉시 적용할 수 있게 됐다.

## 회고

나는 에러가 나는 게 좋다.

정해진 규칙대로 흘러가지 않으면 가차 없이 에러를 뱉어버리는 컴퓨터의 정확함은, 오히려 시스템의 빈틈을 발견하고 프로덕트의 퀄리티를 한 단계 끌어올릴 수 있는 가장 정직한 기회라고 생각한다.

반대로 에러가 났을 때 브라우저가 하얗게 뻗어버리는 것이 두려워 `catch`문으로 어설프게 덮어두거나 조용히 삼켜버리면, 나중에 걷잡을 수 없는 거대한 후폭풍으로 돌아온다. 화면은 멈췄는데 에러 로그조차 남지 않고, 사용자는 데이터를 날리며, 개발자는 깜깜이 디버깅에 갇히게 된다.

세미나를 준비하며 팀원들에게도 이 점을 가장 강조했다. **에러 핸들링의 본질은 에러를 덮어 숨기는 것이 아니라, 컴퓨터가 정직하게 알려준 신호를 제어 가능한 방식으로 안전하게 드러내고 복구하는 것**이다. 비동기 문법의 작은 부주의가 어떻게 전체 애플리케이션을 침묵의 늪에 빠뜨리는지 파고들며, 시스템과 프로세스로 이를 풀어낸 값진 경험이었다.
